# SKILL — triage-service

**Когда:** ежедневно (cron, будни). **Тир:** T1 (разбирает и докладывает; ответ клиенту — отдельный T3-скилл `draft-service-reply`).

## Цель
Дать владельцу ясную картину открытых сервисных обращений: что срочно, что ждёт, кому что.

## Вход
- EAV-сущности типа «сервис-обращение» в статусе «открыто» (через слой ввода `service-request`).
- KB: `service-criteria.md` (рубрика), `heli-models.md`, `clients.md`.

## Шаги
1. Собрать открытые обращения (новые + незакрытые).
2. По каждому: клиент, модель HELI (если есть), тип, краткая суть, контакт.
3. Классифицировать по `service-criteria.md`: запчасть / ТО / гарантия / ремонт.
4. Приоритизировать: 🔴 высокий (машина простаивает / гарантийный отказ ключевого клиента / безопасность), 🟡 средний, ⚪ низкий. Сигналы срочности — из `urgency`/`description`.
5. Для каждого предложить следующий шаг (напр. «→ draft-service-reply», «эскалация: гарантия», «нужны данные: цена запчасти»).
6. Сформировать дайджест по приоритету.

## Выход / формат
```
🛠 СЕРВИС · <дата> · открыто <N> (🔴<h> 🟡<m> ⚪<l>)
🔴 <клиент> · <модель> — <тип>: <суть>; <шаг>
🟡 <клиент> · <тип>: <суть>; <шаг>
NEXT: service-dispatch по <🔴-обращение>; draft-service-reply клиенту <X>
```
> Блок `NEXT:` (опц.) — follow-up подсказки для платформы (F0.5).

## Правила
- НЕ выдумывать обращения/детали — только то, что есть в данных. Нет открытых → честно «открытых обращений нет».
- Цену/наличие запчасти и решение по гарантии НЕ выносить — это эскалация/нужны данные (см. `service-criteria.md`).
- Граница: продажа новой техники → `globerent-sales`; тендеры → `market-analyst`.

## Эскалация
Гарантийный отказ, простой ключевого клиента (см. `clients.md`), безопасность → пометить 🔴 и эскалировать владельцу сразу.
