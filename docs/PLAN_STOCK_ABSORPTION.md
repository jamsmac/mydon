# План поглощения mydon-stock → mydon

Дата: 2026-08-24. Решение владельца: **mydon не должен быть связан с
mydon-stock ничем** — stock остаётся только донором готовых решений, все
функции живут в самом mydon. План построен на полной инвентаризации обеих
кодовых баз и трассировке связей (workflow wf_fe36fe5d, 4 агента, всё с
file:line).

Ключевой принцип порядка: **сначала снимаются зависимости mydon ОТ stock,
потом гасятся пользовательские контуры stock** — каждый только после
появления полноценной замены. Методика владельца действует: считать всё,
что уже можно; чего нельзя — держать в книге «Пробелы», не молчать.

## Срезы

### П1. Опс-развязка бэкап-канала (мал, без риска)
`backup_extra.sh` переводится с бота склада на аварийного бота сторожа
(`WATCHDOG_BOT_TOKEN`/`WATCHDOG_CHAT_IDS` из `/etc/mydon-heartbeat.env`) —
прецедент уже создан в `auto-deploy.sh` (PR #201). Доставка — по `"ok":true`.
Закрывает связь №3. После этого падение/переезд stock не ломает бэкапы mydon.

### П2. Учётный поток OurVend — свой (самый важный срез)
Пока он не сделан, **stock выключать нельзя вообще** — mydon ослепнет по
продажам и приходу.

Перенести в mydon (донор: `app/ourvend.py`):
- суточный снапшот продаж по автоматам и дням (`snapshot_days`) с догоном
  пропусков до 14 дней и идемпотентной перезаписью дня (DELETE+INSERT в
  транзакции);
- утренний снимок остатков слотов (`snapshot_machine_stock`, пагинация Lot
  management, фильтр чужих MId);
- **НОД-дедуп** повторяющихся строк ответа (×1/×2/×3 — тест уже есть у
  донора);
- отказ при >500 строк вместо тихой обрезки; логин без ретраев (риск
  блокировки аккаунта os.ourvend.com).

Писать напрямую в свои `sale` / `machine_stock` тем же каноном серийников
(`machineSerialKeys`). Разместить в `apps/agents` рядом с существующим
синком слотов; у систем сейчас РАЗНЫЕ учётки OurVend — на переходный период
двойного съёма следить за блокировками, целевое состояние — один коннектор,
два потока (учётный суточный + плановый 3-часовой).

Критерий готовности: 7 подряд дней самостоятельного съёма сходятся со
съёмом stock до строки. После этого `STOCK_DATABASE_URL` пустеет, сеть
`mydon-stock_default` снимается из compose (связи №1 и №2 закрыты).

### П3. Закупки — донести бот-мастер до уровня донора
Каркас в mydon уже сильнее (заявка→approval→накладная→приёмка с
распределением в автоматы). Донести из FSM-мастера stock:
- **price gate**: подтверждение при отклонении цены >20% от последней; ✅ П3a
- фото чека с форвардом в архив (у `stock_batch` уже есть `source=receipt`); ✅ П3a
- срок годности позиции при приёмке (для вендинг-товаров); — отложено, см. ниже
- мультипозиционная сессия и подсказки последней цены/количества. — не нужно, см. ниже
Затем гасится синк `purchases` (часть связи №1) и ручные формы панели stock.

**Решения волны П3a (2026-08-24, после инвентаризации 5 измерений).**
Реализовано: (1) команда «цена <товар> <число> [точно]» — гейт ±20%
(`PRICE_SPIKE_PCT`) без FSM, единственный живой писатель
`vending_product.purchasePrice`; (2) мост `receiveOrder` → строки `purchase`
(`source='vending-order'`, цена из снапшота накладной, той же транзакцией,
`received_at`/`received_by` в накладной — миграция 0065) — журнал прихода
переживает отключение синка `purchases`; (3) фото с подписью «чек» →
вложение `ownerType=vending_purchase_order` к последней принятой за сутки
накладной.
Осознанно НЕ реализовано (дубли живых механизмов): ввод фактических цен при
приёмке — факт-деньги уже фиксирует касса закупа §5.8
(`vending_cash_session`); срок годности вендинг-товаров — требует партий в
`vending_stock` (сейчас integer-счётчик), решение о партиях — отдельный
срез; FSM-сессия закупа — процесс mydon другой
(заявка→одобрение→накладная→приёмка), подсказки цен заменяет прайс.

### П4. Полевой снек-контур в боте

**Решения волны П4 (2026-08-25, спека `docs/superpowers/specs/2026-08-25-p4-field-snack-design.md`, рулинги R-P4-1…6).**
✅ мастер «Заполнил автомат» включён и доделан (`staff-refill.ts`: пикер
автомата → чек-лист по плану закупа → «Загрузил по плану» одним нажатием
или правка нумпадом → «другой товар» → «Готово»; пишет `POST /vending/refills`);
✅ усушка — детектор заливок по снимкам слотов (`vending_refill_event`,
миграция 0067, окно 3 ч, идемпотентно по `(serial, window_to)`) и
`GET /vending/shrinkage?days=14` (недостача по дням БЕЗ заливочных событий,
`expected − actual` по товару, порог `SHRINK_ALERT_UZS` по позиции за
период, излишки показаны и в сумму НЕ входят, цена — канон `purchase_price`);
видимость — алерт `vending.shrinkage_alert` в утренний брифинг бота,
команда владельца «усушка», лист CC `reports:shrinkage` + секция на вкладке
«Снек».
Осознанно НЕ реализовано: **инвентаризация автомата задним числом — НЕ
делаем** (R-P4-1) — снимок OurVend каждые 3 ч без пропусков точнее ручного
пересчёта, §1.3 WAREHOUSE_SPEC остаётся в силе; **перемещения между
складами — НЕ делаем** (R-P4-5) — склад вендинга один, `stock_movement.kind
= transfer` — 0 строк за всю историю; появится второй живой склад — отдельный
срез.
Связь №1 (учётный поток): **паритет остатков добавлен** — `GET /ourvend/parity`
несёт блок `stock` (сравнение `ourvend_stock_snapshot` ↔ `machine_stock` по
`(dt, serial, product)`, тот же канон серийника и то же имя товара через
алиасы, что и у продаж); **флип на `own` — ручной шаг после 7 зелёных дней
по ОБОИМ потокам** (продажи и остатки, один флаг `OURVEND_ACCOUNTING_SOURCE`);
после флипа синк `machine_stock` из stock-БД гасится.
7 зелёных дней по остаткам считать только по дням, где `stock.checked > 0`.
**Уточнено волной фиксов (R-FW-2, 25.08):** пустой снимок `ourvend_stock_snapshot`
за день теперь даёт `stock.ok = false` с `note: "снимков остатков OurVend за
период нет — сверять не по чему"` — прежнее «`checked=0` ⇒ `ok=true` по
определению» было ровно той заглушкой, что врёт: гейт «7 зелёных дней»
засчитал бы на проде дни, где ни одна строка не сравнивалась (прод read-only
25.08 подтвердил — `dt < current_date` выбрасывал единственный день снимков
целиком, и половина гейта отдавала «ok» вхолостую). День с `checked = 0`
теперь и не зелёный (веры ему нет), и в счёт семи зелёных дней по-прежнему
не идёт — двойная защита от того же паттерна.

**Выкатка (R-FW-4):** после раскатки миграции 0067 и первого прохода `ingestSlots`
— один раз `node packages/db/dist/backfill-product-ids.js` (резолвит
`product_id` для `vending_stock`/`machine_slot` с `product_id IS NULL` по
`vending_product.name`/`vending_alias` той же нормализацией, что Core;
печатает «обновлено N / осталось NULL M»; идемпотентен). Автодеплой его не
запускает — ручной шаг, как сид П5a.

### П5. Аналитика и отчёты
Донести из `reports.py`: «что купить» с поставщиками/бюджетом (426–528) —
✅ П5a (без поставщика/бюджет-лимита), `dead_stock` 21 день (591),
`price_changes` >5% (622) и динамика цен, **маржа по автоматам**
(567 — заодно закрывает заглушку «Себестоимость» в CC), недельная сводка
+ подписки на рассылки, живая сверка OurVend из бота + `price_gap_report`
(витрина против sale_price).

**Решения волны П5a (2026-08-25).** Реализовано: (1) purchase-first —
потребность автомата сначала закрывается закупом, остаток от заказа (после
округления до блока) добирается со склада (решение владельца 24.08); (2)
правила закупа как данные на товаре вендинга (миграция 0066) —
`excluded_from_purchase` («не закупать»), `fixed_purchase_qty` (фикс-
количество), `pack_size` (блок упаковки), правятся и из бота
(«не закупать/закупать <товар>», «фикс <товар> <N>», «блок <товар> <N>»), и
листом CC `settings:purchase_rules` («Правила закупа»); (3) маршрут обхода
автоматов — настройка `VENDING_ROUTE_ORDER` (серийники через запятую),
источник — панель настроек, база важнее env; (4) автоматы не в строю
(`status != in_service`) отфильтрованы до расчёта потребности; (5) Core
`GET /vending/plan` — общий расчёт для бота и панели, ядро одно, числа не
расходятся; бот — «план закупа» по маршруту и слотам, панель — лист CC
`reports:buy_plan` («План закупа») с маршрутом, купить/склад/убрано,
раскладкой по слотам и кнопкой «Оформить закуп»; позиции заявки несут
`perMachine`/`fromPurchase`/`fromStock`/`unfilled` по каждому автомату.
Осознанно НЕ реализовано (следующая волна П5b, если понадобится): горизонт
склада N дней вперёд (донор 2, `purchase_recommendations`); поставщик и
лучшая цена за 90 дней; `dead_stock`; `price_changes`; маржа по автоматам;
PNG/HTML-картинки плана в Telegram (текстом хватает); нечёткие алиасы
названий товара; редактор цен в CC — единственный писатель цены остаётся
команда бота «цена» (гейт ±20%, `PRICE_SPIKE_PCT`); общие типы ответа плана
в `@mydon/shared` (сейчас форма плана описана трижды: Core, бот, CC);
`fromPurchase` в приёмке
накладной — это П4; фикс-количество принимается без гейта «сильно больше
дефицита» (как у донора).
Сид правил на проде — **вручную, один раз** (R-P5a-5):
`docker compose -f deploy/docker-compose.yml run --rm mydon-core node
packages/db/dist/seed-vending.js`, автодеплой его не запускает.

**Волна фиксов П5a (после финального и адверсариального ревью).** Повторный
прогон сида НЕ трогает строки, изменённые владельцем: правило накладывается
только на «нетронутую» строку (`excluded_from_purchase = false`,
`fixed_purchase_qty IS NULL`, `pack_size` = дефолт категории), остальные
печатаются как пропущенные — иначе выкатка молча возвращала бы «блок 12»
товару, которому владелец вчера поставил 6.

**Хвосты П5b (2026-08-25).** Восемь мелких правок после ревью П5a, все с
тестами: (1) `sales_partial` сужен — предупреждение только когда в свежем
батче продаж НЕТ автомата, у которого в плане есть потребность, и автоматы
названы именами («В свежем батче продаж нет автоматов: Olma — по ним «нет
продаж» может быть ложным»); прежнее «в батче меньше, чем в расчёте» горело
на ровном месте: полный автомат продаж мог и не прислать; (2)
`machine_skipped` — ОДНА строка на все автоматы не в строю («Не в строю, в
план не вошли: SKLAD 4S (В ремонте), SKLAD 5S (На складе)», по имени), на
проде три SKLAD-автомата давали три вечных предупреждения в каждом плане;
(3) фильтр «в строю» распространён на `forecast()` и `deficitSummary()` —
то же множество автоматов, что у `purchase()`/`plan()`; `machines()` НЕ
фильтруется (список — зеркало сбора Ourvend), но каждая строка несёт
аддитивное `inService: boolean`; (4) у гейта двойной заявки на закуп
появился TTL `PENDING_PURCHASE_TTL_DAYS = 3`: блокирует только свежая
заявка, и в причине стоит дата («уже ждёт решения (с 24.08)»), — забытая
заявка недельной давности молча запирала СОВСЕМ ДРУГОЙ поход; (5) строки
`vending_stock` сопоставляются с прайсом по НОРМАЛИЗОВАННОМУ имени
(`normalizeProductName`, как `findProductRow`): «Red  Bull» с двойным
пробелом объявлялся осиротевшим при живой карточке, и остаток не вычитался
из потребности; (6) товары без карточки прайса больше не дублируются в
`no_price` — у них остаётся один совет, из `unknown_product`; (7) в панели
секция «Убрано из закупки» не повторяет «со склада N» (цифра уже стоит в
«Собрать со склада», как в боте); (8) эта запись и §6 спеки П5a.

У позиций **без цены** кратность теперь берётся из блока товара (раньше — 1):
«купить N ед» по таким позициям вырастет до кратного блоку. Сумма закупа не
меняется — позиции без цены в деньги не входят по-прежнему (R-P5a-7).

  `STOCK_DATABASE_URL` не задан — без зеркала другого пути нет); на проде

  `"default"` — compose подставляет фолбэк `stock` прямо в переменную
  окружения контейнера), `GET /system/config` несёт ещё и `effective`;
- **фильтр «в строю»** в записи `machine_stock` режима `own` — складской
  автомат SKLAD 4S (`2508160360`, `status='warehouse'`) больше не даёт
  +34 фантомных строки/сутки на 7028 «единиц» заглушки; для режима `stock`
  поведение не изменилось;
- **сторож свежести учётного снапшота** — следит РАЗДЕЛЬНО за
  `max(fetched_at)` таблиц `ourvend_sale_snapshot` и `ourvend_stock_snapshot`:
  если агент `ourvend:accounting` не приносит суточный снимок кабинета
  дольше `SNAPSHOT_STALE_HOURS` (36 ч) хотя бы по одной из них, событие
  `ourvend.snapshot_stale` называет, какая («продаж»/«остатков»/«продаж
  и остатков»), вместо тихой остановки `sale`/`machine_stock` без
  единой ошибки;
- **еженедельная ретенция** (`slot_snapshot`, `product_sale`,
  `machine_sale`, `vending_sync_run` — вс 04:10 Ташкент, `event`/`raw_row`
  не трогаются);
- **рунбук `docs/CUTOVER.md`** — шаги 0–4 катовера, у каждого команда,
  ожидаемое число и откат.

**Сам флип `OURVEND_ACCOUNTING_SOURCE=own` в этом срезе НЕ ВЫПОЛНЕН.**
Продовых записей срез не делает ни одной. Самая ранняя физически возможная
дата — **2026-09-01, 08:40 Ташкент** (семь зелёных суток подряд от первой
полной сверки 26.08.2026); флип выполняет владелец по `docs/CUTOVER.md`
не раньше этой даты.

#### П8.2 — сторожа переехали на пути mydon (код готов)

Вынесено вперёд из П8: связь №4 не требовала замены функциональности и держала
сторожей заложниками чужого каталога. Хостовая копия `disk_guard.sh` отстала от
git на месяц именно поэтому — деплой mydon в `/opt/mydon-stock` не заглядывает.

Сделано в репозитории:

- `deploy/guards/disk_guard.sh` и `deploy/guards/healthz_guard.sh` берут ключи
  ТОЛЬКО из окружения mydon (`/opt/mydon-app/.env` → `/etc/mydon-heartbeat.env`),
  бота склада больше не читают и без конфигурации выходят ненулём с причиной в
  `/opt/backups/backup.log`;
- `deploy.sh` и `auto-deploy.sh` ставят обоих сторожей в `/opt/backups` тем же
  механизмом, что `backup_extra.sh` — то есть каждым деплоем;
- `deploy/setup-guards.sh` — идемпотентный установщик cron с `--dry-run`,
  бэкапом прежнего crontab и отказом указывать расписание в пустоту;
- тесты `deploy/tests/setup-guards.test.sh` и `deploy/tests/guards-env.test.sh`
  в шаге CI «Operations scripts».

Остаётся ручным шагом ПОСЛЕ мержа (cron деплой не трогает и трогать не должен):
`/opt/mydon-app/deploy/setup-guards.sh --dry-run`, затем без флага. Строки
склада (`backup_offsite.sh`, `restore_test.sh`) установщик не трогает — они
уходят в П8 вместе с базой склада.

**Сторож застоя сбора `ourvend.sync_stale` (П8a, отдельно от host-сторожей
выше).** Не хостовый cron-скрипт, а `SyncStaleService` внутри самого Core
(`*/30 * * * *`, Asia/Tashkent): если последнего успешного прогона синка
OurVend не было `SYNC_STALE_HOURS` часов (настройка, по умолчанию 6) — событие
`ourvend.sync_stale`, дедуп раз в ташкентские сутки, правило `immediate`.
Закрывает дыру, из-за которой 24–25.08.2026 сбор простоял 12 отказов подряд
незамеченным: `ourvend.sync_failed_streak` (П5b) ловит явные `failed`, а
зависший или не запускающийся коллектор (нет ни `failed`, ни `success`) не
ловил никто. `OurvendHealth.staleHours`/`staleThresholdH` — те же числа в
`GET /ourvend/health`, боте («сверка») и панели («Здоровье сбора»).
