# Активация агентов MYDON — runbook владельца

Все «умные» части агентов построены и покрыты тестами, но **спят по умолчанию**:
без ключей/шлюзов агенты работают детерминированно (смотрят Core, предлагают
дело, молчат когда повода нет). Этот файл — единственная точка правды: какие
тумблеры щёлкнуть, чтобы включить мозг, память и самоулучшение, и что каждый
включает.

Принцип безопасности сквозной: **агент ничего не делает сам** — он пишет событие
и создаёт запрос на согласование (HITL). Автономия по умолчанию `T0` (только
предлагает). LLM-шлюзы и embed-модель держать **только внутри Tailscale**.

## Два способа щёлкать тумблеры

- **Из панели** (`Система · Активация`) — не-секретные глобальные тумблеры
  (мозг/RAG/пауза/бюджет/автономия) хранятся в базе Core и **перекрывают `.env`**.
  Правки действуют без пересборки: агенты накладывают их при перечитке. Это
  рекомендуемый путь для владельца — с телефона, без доступа к серверу.
- **Через `.env`** — то же самое на уровне окружения (когда базы ещё нет или для
  первичной настройки). Внутри одного ключа приоритет: **база > env > дефолт**.
  Для переименованного глобального лимита новый `LLM_GLOBAL_DAILY_BUDGET_USD`
  как группа важнее legacy `AGENT_GLOBAL_BUDGET_USD`; пустой новый ключ сохраняет
  старое значение как переходный fallback.
- **Секреты (API-ключи) — только `.env`.** В панели их принципиально нет
  (правило ТЗ). `LLM_PRICE_PROVIDER_ID` и `EMBED_PRICE_PROVIDER_ID` доступны в
  панели, потому что это не ключи и не URL, а literal ID ценового профиля из
  `llm_model_price.provider`. Для рабочего metered HTTP-пути секрет шлюза
  остаётся только в `.env`.
- `LLM_HTTP_BILLING_MODE` и `EMBED_BILLING_MODE` тоже намеренно **только в
  `.env`**. Значение `local` обходит денежный ledger, поэтому этот опасный
  monetary bypass нельзя включить случайным кликом из панели.

## Сценарий 1 — CLI-подписка временно недоступна

Anthropic может после исчерпания лимита подписки продолжить работу за
usage credits по стандартным API-тарифам. `claude auth status --json`
подтверждает OAuth, но не возвращает структурный флаг
`extra_usage.is_enabled` до model dispatch. Поэтому `claude-cli`,
`claude-subscription`, `codex-cli` и `gemini-cli` заблокированы fail-closed:
ни наличие OAuth-токена, ни установка CLI не разрешают child process.

Для агентов используй метрируемый HTTP-путь из сценария 1б. Вернуть CLI
можно будет только после появления стабильного машиночитаемого preflight,
который до каждого turn доказывает, что usage credits выключены.

[Как Anthropic биллит usage credits](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans).

Что оживает после настройки HTTP: навык `assess-ideas` (оценка фишек канала моделью) и петля coach
(EVAL/PROPOSE). Без шлюза оба честно спят.

## Сценарий 1б — включить платный HTTP-шлюз

1. Выбрать literal ID ценового профиля (например, `anthropic`) и добавить в
   серверный каталог `llm_model_price` действующую цену с этим exact `provider`
   для **каждого SKU, куда шлюз способен маршрутизировать запрос**, а не только
   для значений `LLM_MODEL` / `LLM_FALLBACK_MODELS`. Provider ID —
   исчерпывающий routing contract. Для `agents`/`embeddings` Core резервирует
   максимум по всем активным SKU этого provider; settlement сохраняет snapshot
   запрошенной модели и сверяет фактическую модель провайдера. Делать изменение
   цены отдельной миграцией: старую строку закрывать через `valid_to`, новую
   вставлять отдельно. Если exact запрошенной цены нет, Core fail-closed
   отклонит reserve и провайдер не будет вызван.
2. В `.env`:
   ```
   LLM_BASE_URL=http://<tailscale-host>:<port>
   LLM_PRICE_PROVIDER_ID=anthropic       # exact llm_model_price.provider; не URL/секрет
   LLM_MODEL=<имя-из-каталога>
   LLM_API_KEY=<секрет-если-нужен>
   LLM_HTTP_BILLING_MODE=metered
   ```
3. Проверить глобальный потолок `LLM_GLOBAL_DAILY_BUDGET_USD` и, для Agents,
   `AGENT_DAILY_BUDGET_USD` либо `budget.per_day_usd` в карточке агента.

`LLM_HTTP_BILLING_MODE=local` обходит денежный ledger и потому разрешён только
для runtime, который действительно работает локально и не выставляет счёт.
В этом режиме `LLM_PRICE_PROVIDER_ID` можно не задавать. В `metered` отсутствие
ID — ошибка конфигурации до reserve и HTTP-вызова; никакого неявного
`openai-compatible` нет. Успешный ответ обязан сообщить фактическую модель;
отсутствие `usage.cost` не считается доказательством нулевой цены. Core сам
классифицирует неполный или несовместимый settlement и при routing anomaly
открывает provider circuit до ручной сверки либо новых ташкентских суток.

## Preflight перед включением Bot / CC / Documents

Эти три поверхности используют `MYDON_ASSISTANT_MODEL` и Anthropic. Перед
rollout миграции проверь значение ключа в production `.env`:

- пустое значение возьмёт штатную модель, для которой миграция уже содержит
  цену;
- непустое значение должно иметь действующую exact/dated строку
  `provider=anthropic` в `llm_model_price`;
- старый произвольный override (например, модель 4.x без строки каталога) после
  включения ledger будет намеренно отклонён fail-closed до вызова провайдера.

Сначала применить миграцию и проверить каталог, затем перезапускать
`mydon-core`, Bot и CC. Не добавляй «примерную» цену только ради прохождения
проверки: тариф должен быть отдельной версионированной миграцией.

## Сценарий 2 — включить семантическую память (RAG)

1. Поднять OpenAI-совместимый `/embeddings` (локальная модель в Tailscale или
   облачный endpoint).
2. В `.env`:

   ```
   EMBED_BASE_URL=http://<tailscale-host>:<port>
   EMBED_PRICE_PROVIDER_ID=openai        # exact llm_model_price.provider; не URL/секрет
   EMBED_MODEL=text-embedding-3-small     # или своя
   # EMBED_API_KEY=...                     # если endpoint требует
   EMBED_BILLING_MODE=metered             # default; local только для локальной модели
   ```

   Для metered-модели нужна действующая строка с
   `provider=$EMBED_PRICE_PROVIDER_ID` в `llm_model_price`, по тем же правилам,
   что в сценарии 1б. Без ID embedding блокируется до provider; при
   `EMBED_BILLING_MODE=local` ID можно оставить пустым.

Что оживает: `assess-ideas` перед оценкой **вспоминает похожие уже разобранные
идеи** и просит модель не повторять их, а после — запоминает разобранные посты.
Хранение — в журнале Core (переживает рестарт). Векторы разной длины/битые
считаются несовпадением (0) — память не «галлюцинирует» совпадения.

Граница инъекций сохранена: пересказ прошлых постов — тоже внешний текст, идёт в
**недоверенный** блок под маркером, доверенная инструкция лишь просит не
повторять.

## Сценарий 3 — самоулучшение (coach) и применение правок

Петля: coach судит последнее действие агента по рубрике → при «improve»
предлагает правку `SKILL.md` (SEARCH/REPLACE diff) → владелец одобряет →
правка ложится git-коммитом.

- **Судья** (`coach-review`) оживает вместе с мозгом (Сценарий 1). `coach-agent`
  уже `active`, расписание еженедельное. Правка НЕ применяется сама — приходит
  предложением в очередь (diff в фактах). Безопасность 1–2 по рубрике → эскалация
  без правки. Судья не судит сам себя.
- **Применение** одобренной правки — отдельная деливерейт-операция **там, где
  есть репо и git** (обслуживающий скрипт / CI / машина владельца), НЕ в
  эфемерном проде:
  ```
  pnpm --filter @mydon/agents coach:apply -- <агент>/skills/<навык>.md <файл-с-diff>
  ```
  Инварианты (все проверяются): path-guard (только `<агент>/skills/<навык>.md`
  известного агента), каждый блок diff указывает на тот же файл, SEARCH
  символ-в-символ, коммит только при успехе, git-откат. Правится **только**
  `SKILL.md` — никогда код/config/ROLE/факты.

## Проверка «включилось ли»

При старте `apps/agents` печатает позы (posture) LLM-пути, бюджета и coach —
видно, что активно, а что спит. Если тумблер задан, но навык молчит, порядок
проверки: (1) `ideaChannels`/`webSources` в паспорте не пусты, (2) канал/сайт
реально читается, (3) `AGENTS_SCHEDULES_PAUSED=0`, (4) для metered HTTP —
pricing profile существует и Core разрешает reserve до provider.

Ничего не задано → это не поломка: агенты работают детерминированно, очередь
остаётся сигналом, а не лентой.

## Durable checkpoint и Notion outbox (миграция 0076)

Этот контур действует только для **задачи, порученной агенту через Core**. После
успешного ответа checkpoint endpoint Core хранит неизменяемый результат навыка
(`proposal` либо `no_signal`), его hash, исходный task-input hash и устойчивый
`executionAttemptId`. Если worker упал или lease перехватил другой worker,
следующий claim получает этот checkpoint и продолжает с него: навык и LLM
повторно не запускаются.

Следующий шаг — один атомарный commit в PostgreSQL. Fence текущей generation,
результат и статус задачи, применимые event/memory/approval и intent публикации
отчёта в Notion либо фиксируются вместе, либо не фиксируется ничего. Точный
повтор с тем же payload возвращает прежний результат; другой payload для того
же `executionAttemptId` считается конфликтом. Notion вызывается только после
commit отдельным dispatcher, поэтому сбой Notion не откатывает выполненную
задачу и не теряет её внутренний результат.

Граница гарантии находится **после подтверждённого checkpoint**. Между ответом
LLM/provider и приёмом checkpoint Core нет общей транзакции и нет
exactly-once: процесс может получить платный ответ и умереть до записи. Ledger
не даёт автоматике вслепую сделать второй оплачиваемый вызов, но восстановить
не записанный provider output не может; такая попытка остаётся
`execution_unknown` до решения владельца.

В этот slice пока **не входят** cron-запуски навыков, Assistant, Documents и
доставка Telegram. У них нет task checkpoint/atomic commit из 0076. Notion
report — единственный внешний destination нового outbox; наличие таблиц не
означает, что Telegram или документы уже получили durable delivery.

### Состояния Notion outbox

| Состояние     | Значение                                                                              | Действие оператора                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending`     | Intent создан в той же транзакции, что outcome задачи                                 | Ничего не менять: dispatcher заберёт его по FIFO                                                                                            |
| `dispatching` | Core выдал delivery по lease **до** запроса в Notion                                  | До 15 минут ждать завершения; если старше — запустить/восстановить один dispatcher и затем разбирать как `unknown`, не возвращать в pending |
| `sent`        | Notion подтвердил создание, `provider_ref` сохранён                                   | Ничего                                                                                                                                      |
| `skipped`     | Notion не настроен; внутренний outcome задачи уже сохранён                            | Настроить Notion для будущих delivery; этот intent автоматически не повторяется                                                             |
| `unknown`     | Timeout/обрыв, `409`, `5xx` либо просроченный `dispatching`: страница могла создаться | Вручную искать отчёт в Notion по заголовку и времени; не найдено — владелец отдельно решает о новой доставке, принимая риск дубля           |
| `dead`        | Явный `400/401/403/404`, исчерпаны bounded `429` retry или невалидный payload         | Проверить `last_error`, исправить причину и создавать только новую осознанную delivery, не переписывать старую строку                       |

Просроченный `dispatching` при следующем claim переводится в `unknown`, а не
обратно в `pending`: Notion create не имеет доказанной exactly-once
идемпотентности. Только `429` повторяется до двух раз внутри того же
claim с учётом `Retry-After`: такой ответ явно отклонил запрос. Для разбора
смотреть строки и логи вместе:

```bash
/opt/backups/db_access.sh query "
select id, key, status, attempts, claimed_at, completed_at, provider_ref, last_error
  from outbox_delivery
 where destination = 'notion-report'
   and status in ('dispatching', 'unknown', 'dead')
 order by created_at"
docker logs --since 30m mydon-agents 2>&1 | grep -i 'notion\|outbox'
```

Нельзя чинить инцидент прямым `UPDATE ... status='pending'`: это стирает
неоднозначность и может создать вторую страницу. Старую строку оставляют как
аудит; повтор — только отдельное решение владельца после сверки Notion.

## Если задача durable-заблокирована

Причина видна в карточке и `agent_execution_blocked_reason`. Block возникает, если
ledger уже видел физическую LLM-попытку без durable output, после checkpoint
изменили задачу/исполнителя, владелец вернул committed-работу на redo или у
агента нет подходящего навыка. Автоматика намеренно не вращает execution attempt:
это могло бы повторить оплату или применить устаревший результат.

1. При первичной настройке создать отдельный секрет, например
   `openssl rand -hex 32`, и записать его как `OWNER_ACTION_TOKEN` в `.env`.
   Он обязан отличаться от `SERVICE_TOKEN` (равенство блокируется кодом).
   Compose передаёт его только Core; не добавлять его Bot/Agents/CC.
2. Проверить `agent_execution_blocked_reason` задачи и финансовую строку
   `llm_spend` по `task:<taskId>:execution:`. Если прошлый результат уже был
   доставлен, retry не нужен.
3. Если владелец осознанно разрешает потенциально повторную оплату, вызвать:

   ```sh
   curl -X POST "http://127.0.0.1:3001/tasks/<task-id>/agent-run/retry" \
     -H "x-service-token: $SERVICE_TOKEN" \
     -H "x-owner-action-token: $OWNER_ACTION_TOKEN"
   ```

Маршрут fail-closed при пустом owner token и пишет
`task.agent_execution.retry` в audit log. Передавать `actor:"owner"` в JSON
недостаточно и больше не поддерживается.
