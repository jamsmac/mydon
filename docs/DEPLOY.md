# Развёртывание MYDON на MYDON/OS

**Сервер:** Hetzner (Helsinki) + Tailscale, `100.81.197.68`.
**Состояние на 2026-07-26 (замер):** 4 ядра / 7.6 ГБ RAM / 38 ГБ диск,
занято 25 ГБ (70%), свободно 11 ГБ, нагрузка 0.24, работает 13 контейнеров.
Docker есть, Node на хосте НЕ установлен — поэтому разворачиваем контейнерами.

Managed primary и локальная recovery-БД используют PostgreSQL 17. Старый PG16
volume после migration сохранён, но Compose к нему больше не подключается.

Портов наружу не открываем (ТЗ §6): Core слушает `127.0.0.1`, бот работает
через long polling. Доступ — только через Tailscale.

## Перед первым запуском

1. Заполнить на сервере файл `.env` рядом с репозиторием:

```
POSTGRES_PASSWORD=<длинный пароль>
DATABASE_MODE=local
DATABASE_URL=postgresql://mydon:<тот-же-пароль>@mydon-db:5432/mydon
DATABASE_ADMIN_URL=
DATABASE_SIZE_WARN_MB=400
TELEGRAM_BOT_TOKEN=<токен бота>
TELEGRAM_ALLOWED_CHAT_IDS=<твой chat_id>
INGEST_KEY=<случайный ключ для приёма внешних событий>
SERVICE_TOKEN=<случайный токен: openssl rand -hex 32>
AGENT_AUTONOMY_MAX=T0
AGENTS_SCHEDULES_PAUSED=1
```

`SERVICE_TOKEN` обязателен. Core отклоняет любую запись (POST/PATCH/PUT/DELETE)
без него — 401, чтения при этом работают. Один и тот же токен из `.env` compose
раздаёт Core, панели, боту и агентам сразу, поэтому задавать его нужно в одном
месте, но ДО первого `up -d`: иначе панель и бот поднимутся с пустым токеном и
запись откажет, пока контейнеры не пересоздадут.

`AGENT_AUTONOMY_MAX=T0` и `AGENTS_SCHEDULES_PAUSED=1` — осознанные значения:
агенты только предлагают и не запускаются по расписанию, пока владелец не решит иначе.

Мозг, память и бюджет агентов включаются отдельными тумблерами `.env` —
их карта и сценарии в `docs/AGENTS_ACTIVATION.md`. Все они уже прокинуты в
контейнер `mydon-agents` (`deploy/docker-compose.yml`) и по умолчанию спят.

Для managed PostgreSQL используется `DATABASE_MODE=external`. `DATABASE_URL`
должен вести через session pooler и используется только Core; прямой TLS URL
кладётся в `DATABASE_ADMIN_URL` и доступен только host-level backup/restore
helper. URL и пароли не передаются аргументами команд. Актуальная схема,
переключение и откат описаны в [`DATABASE_DR.md`](DATABASE_DR.md).

## Мозг помощника: подписка Claude или API-ключ

Помощник (панель и бот) понимает свободные вопросы, если задан хотя бы один
способ входа. Оба вписываются в тот же `.env` (значения вносит только владелец):

```
CLAUDE_CODE_OAUTH_TOKEN=<токен подписки — команда: claude setup-token>
ANTHROPIC_API_KEY=<платный API-ключ с console.anthropic.com>
```

- **Подписка** — та же, что у Claude Code на Маке, отдельно не оплачивается.
  Токен выдаёт команда `claude setup-token` (запускается на Маке, вход через
  браузер; токен действует год). Расход идёт в лимиты подписки.
- **API-ключ** — платный, поштучно за запросы. Нужен ТОЛЬКО для документов
  (Excel/Word-отчёты агентов): их делают серверные навыки Anthropic, которых
  в подписке нет. Для вопросов-ответов помощника не обязателен.
- Заданы **оба** — вопросы идут через подписку, а при её сбое или исчерпании
  лимита незаметно отвечает API-ключ.

После правки `.env` перезапустить панель и бота:

```bash
cd /opt/mydon-app && docker compose -f deploy/docker-compose.yml --env-file .env up -d mydon-cc mydon-bot
```

2. Проверить свободное место: нужно ~1.5 ГБ на образ и базу. Сейчас 11 ГБ — хватает.

## Миграции

```bash
docker exec -i mydon-core node packages/db/dist/migrate.js # применить схему
docker exec -i mydon-core node packages/db/dist/seed.js    # только 5 направлений
```

Production-скрипты запускают эти команды одноразовыми контейнерами из нового
образа до переключения сервисов. `migrate.js` печатает ошибку PostgreSQL и
проблемный запрос; `drizzle-kit migrate` для операционного запуска не используем.

### Разовый перенос истории склада (П8a)

Миграция 0069 заводит таблицу `vending_stock_count`, но сами исторические
строки миграция не приносит — их переносит отдельный **идемпотентный**
скрипт, и автодеплой его НЕ запускает (запускать руками, один раз, после
того как 0069 уже применена):

```bash
docker exec -i mydon-core node packages/db/dist/import-stock-history.js --dry-run </dev/null
docker exec -i mydon-core node packages/db/dist/import-stock-history.js --apply   </dev/null
docker exec mydon-stock-db-1 pg_dump -U mydon mydon | gzip > /opt/backups/stock-archive/$(date +%F).sql.gz
```

Порядок обязателен: сначала `--dry-run` (отчёт, ничего не пишет) — смотреть
числа в выводе; расхождение с ожидаемым означает, что донор изменился после
последней сверки, и решать это данными, а не флагом. Потом `--apply` (пишет
`vending_refill`/`vending_stock_count`, добивает недостающие `purchase` по
`ext_id`). Повторный `--apply` обязан дать нули по всем счётчикам — это и
есть доказательство идемпотентности. Только ПОСЛЕ переноса — архив: `pg_dump`
донора в `/opt/backups/stock-archive/<дата>.sql.gz` (запись на ФС хоста, не в
БД mydon); пустой `.sql.gz` значит, что дамп упал, а пайп это молча скрыл —
проверять размером (`ls -lh`), не только кодом возврата.

`</dev/null` в конце каждой команды обязателен: без него шаг может повиснуть
на открытом stdin внутри `docker exec -i`, и висит молча, без ошибки.

Проверка после `--apply`: `GET /vending/stock-counts?days=730` → **460**
строк (потолок окна поднят волной фиксов с 365 до 730 суток — начальный
остаток донора старше 365 суток от текущей даты и не читался бы вовсе;
дефолт без параметра остаётся 90). Не разрешённых по имени — **≤ 11 имён
/ 15 строк** после резолва донора и по `products.name`, и по точному
алиасу `products.ourvend_name`.

**Смоук импорта — только на scratch-БД.** `tools/smoke-import.mjs` (CI, шаг
после `backfill-product-ids.js`) сам заводит фикстурного донора и удаляет
за собой; чтобы разовый запуск руками не мог случайно завестись поверх
боевой БД (например через SSH-туннель на `localhost:5432`), смоук требует
явный `SMOKE_SCRATCH=1` в окружении (CI его выставляет) либо имя базы,
начинающееся с `p8asmoke_`/содержащее `smoke` — без этого он отказывает до
первого запроса. Застава при отказе печатает только **host** подключения
(`new URL(url).host`), никогда полную строку `DATABASE_URL` с паролем — ни в
своём сообщении, ни в выводе дочернего процесса.

Детали, ожидаемые числа отчёта и рулинги — `docs/superpowers/specs/2026-08-25-p8a-stock-history-design.md`
(§6 «Выкатка», аддендумы, включая «Уточнения после adversarial»).

### Катовер учёта OurVend (П8b)

Переключатель источника `sale`/`machine_stock` (`OURVEND_ACCOUNTING_SOURCE`,
`stock`/`own`) живёт в панели **«Система»** (`system_config`, база важнее
env, кеш чтения ≤ 60 с) — переключается без рестарта `mydon-core`.
Последовательность катовера, проверки и откат на каждом шаге —
[`docs/CUTOVER.md`](CUTOVER.md), а не этот раздел; здесь — только карта
новых ключей и то, что автодеплой этого шага НЕ запускает.

Новые ключи панели «Система» (все — `база > env > дефолт кода`, четвёртый
приоритетный уровень после `OURVEND_ACCOUNTING_SOURCE`, `VENDING_ROUTE_ORDER`,
`SYNC_STALE_HOURS`):

| Ключ | Дефолт | Что регулирует |
|---|---|---|
| `OURVEND_ACCOUNTING_SOURCE` | `stock` | источник `sale`/`machine_stock`; без `STOCK_DATABASE_URL` действует `own` независимо от значения |
| `CUTOVER_GREEN_DAYS` | `7` | порог серии зелёных дней паритета для сигнала `ourvend.cutover_ready` |
| `STOCK_PARITY_TOLERANCE` | `3`, не может быть отрицательной | допуск сверки остатков: зеркало (07:50) и агент (08:05) видят один и тот же живой экран автомата с разницей 15 мин, продажа внутри этого окна — не расхождение, если `stock.qty − own.qty` не превышает порог |
| `SNAPSHOT_STALE_HOURS` | `36` | порог сторожа застоя учётного снапшота (`ourvend.snapshot_stale`, только в режиме `own`), считается РАЗДЕЛЬНО по `ourvend_sale_snapshot` и `ourvend_stock_snapshot` — застой любой из двух таблиц эмитит событие, текст называет какую |
| `SNAPSHOT_RETENTION_DAYS` | `180`, панель не примет ниже `90` | окно еженедельной ретенции снимков |

На проде `OURVEND_ACCOUNTING_SOURCE` до первой правки владельца в панели
показывает `source: "env"`, не `"default"`: `deploy/docker-compose.yml`
подставляет `OURVEND_ACCOUNTING_SOURCE: ${OURVEND_ACCOUNTING_SOURCE:-stock}`
— в контейнер всегда попадает непустая переменная окружения, даже если
её нет в `.env` хоста, и слой `default` конфиг-спеки для этого ключа на
проде недостижим. `GET /system/config` для этого ключа отдаёт ещё и
`effective` — действующий источник с учётом фолбэка `own` без
`STOCK_DATABASE_URL` (панель показывает именно его, не сырое `value`).

`GET /ourvend/health` несёт новые поля `parityStreak`, `cutoverThreshold`,
`snapshotStale` рядом с прежними `staleHours`/`staleThresholdH` (П8a) —
разные сторожа отвечают на разные вопросы: «сбор жив?» (П8a) vs «серия
паритета готова к флипу?» и «учётный снапшот в режиме `own` не протух?»
(П8b). Туда же входит `parity.mode`: `"mirror"` — источник ещё `stock`;
`"own-vs-donor"` — источник `own`, но `STOCK_DATABASE_URL` ещё задан, и
сверка идёт с таблицами донора (`ourvend_sales`/`ourvend_machine_stock`)
напрямую, а не с `sale`/`machine_stock`; `"retired"` — переменная снята
(шаг 3 `docs/CUTOVER.md`), зеркала нет, сверять больше не с чем: серия
не считается и `ourvend.cutover_ready` не эмитится. Отдельного GET на
ретенцию нет — конфигурация видна в `GET /system/config`, результат
каждого прогона — в журнале событий, `system.retention {table, deleted,
olderThanDays}`.

**Ретенция ходит сама, автодеплой её не запускает и не может.** Крон
внутри Core, воскресенье 04:10 Ташкент (`RetentionService`, тот же паттерн
`Cron`+`onApplicationShutdown`, что у `ShrinkageService`) — первый прогон
после выкатки этого среза придётся на ближайшее воскресенье; переносить
или запускать вручную незачем, отдельного скрипта или ручного шага здесь
нет.

## Автодеплой (телефон-цикл)

С 2026-07-30 сервер сам выкатывает изменения — чтобы владелец мог ставить задачи
с телефона (claude.ai/code), а принятые в `main` изменения попадали на живой
сервер без Мака.

**Как работает.** systemd-таймер `mydon-autodeploy` каждые 30 секунд запускает
`deploy/auto-deploy.sh` на сервере. Скрипт тянет `main` из GitHub read-only
deploy-ключом; если появился новый коммит — делает `pg_dump` базы, обновляет код,
собирает новый образ, применяет миграции и структурный сид одноразовыми
контейнерами, переключает сервисы и проверяет точные production-имена и health.
Замок `flock` не даёт двум auto-deploy идти разом.

**Сколько ждать.** Раньше любой коммит стоил ~5 минут полной пересборки; теперь:

| Что изменилось в коммите | Что делает деплой | Время |
|---|---|---|
| только `data/`, `docs/`, `*.md` | `git reset`, и всё | ~5 с |
| код одного приложения | пересборка только его (кеш turbo), рестарт | ~40 с |
| зависимости, Dockerfile, схема БД | полная сборка, миграции, рестарт | ~5 мин |

Держится это на трёх вещах: сиды и выгрузки приезжают в контейнер **томом**
`../data:/app/data:ro` (в образе их нет — см. `.dockerignore`), кеш turbo живёт
между сборками через BuildKit cache mount, а шаг 0 скрипта распознаёт коммиты
«только данные/документы» и пропускает сборку. Правило узкое: любой файл вне
трёх путей — полный деплой; пустой список изменений (сбой `git diff`) — тоже
полный деплой, потому что пропустить сборку по неизвестному диффу опаснее.

**Обновить только данные** (после мержа сида): дождаться тика таймера и звать
импорт — пересборки не будет.
```
journalctl -u mydon-autodeploy -n 5 --no-pager   # «только данные/документы»
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node tools/import-globerent-registry.mjs
```

**Ничего наружу.** Вебхуков нет, портов в интернет не открывали. Сервер сам
инициирует соединение к GitHub. Панель по-прежнему доступна только в Tailscale.

**Первичная настройка:** `deploy/setup-autodeploy.sh` на сервере (создаёт
deploy-ключ, делает `/opt/mydon-app` git-репозиторием `main`, включает таймер).
Публичную часть ключа один раз добавить в GitHub → Deploy keys (read-only).

**Наблюдать/управлять:**
```
journalctl -u mydon-autodeploy -n 50        # что делал автодеплой
systemctl list-timers mydon-autodeploy      # когда следующий тик
systemctl stop mydon-autodeploy.timer       # временно выключить
```
Бэкапы перед миграциями: `/opt/backups/mydon-autodeploy/pre_*.sql.gz` (последние 10).

После обновления git-копии auto-deploy также устанавливает актуальные
`deploy/guards/db_access.sh`, `deploy/guards/backup_extra.sh`,
`deploy/guards/b2_offsite.sh`, `deploy/guards/disk_guard.sh`,
`deploy/guards/healthz_guard.sh` и
`deploy/restore_test_mydon.sh` в `/opt/backups`. Cron запускает именно эти
стабильные пути, поэтому без данного шага исправления backup/restore оставались
бы только в рабочей копии репозитория.

Сторожа диска и здоровья попали в этот список позже остальных (П8.2 плана
поглощения): их хостовые копии лежали в `/opt/mydon-stock/`, куда деплой mydon
не заглядывает, и `disk_guard.sh` на сервере отстал от git на месяц. Сам cron
деплой не трогает никогда — расписание переводится разово установщиком
`deploy/setup-guards.sh` (`--dry-run` показывает diff crontab). Пути, ключи и
откат — в [`BACKUPS.md`](BACKUPS.md), раздел «Сторожа mydon: пути, cron, env».

Ручной `deploy/deploy.sh` на время работы останавливает timer auto-deploy, ждёт
завершения уже начатого service и возвращает timer через `EXIT`-trap. Это
предотвращает две одновременные сборки одного `mydon:latest`. Migration и seed
дополнительно используют уникальные имена контейнеров, поэтому хвост прошлого
оборванного запуска не блокирует следующий deploy. После `compose up` оба
сценария требуют контейнеры `mydon-db`, `mydon-core`, `mydon-bot`, `mydon-agents`
и `mydon-cc` в состоянии `running` именно под этими именами. Временное имя,
оставшееся после прерванного Compose replacement, исправляется пересозданием
только затронутого сервиса.

## Пошагово: подключиться к серверу и выкатить

Порядок для случая «PR смержен в `main`, надо чтобы это заработало в поле».
Занимает 5–10 минут, из них большая часть — ожидание сборки.

**Главное, что надо знать заранее:** автодеплой выкатывает **код**, но
**`.env` не трогает никогда** (`auto-deploy.sh`: `git clean -fd -e '.env*'`).
Секреты не в git, и подставить их деплою неоткуда. Поэтому любой PR, который
добавил переменную окружения, требует ручного шага — иначе контейнер поднимется
с пустым значением и промолчит.

### 1. Подключиться

Сервер закрыт: портов наружу нет, вход только через Tailscale.

```bash
tailscale status | grep mydon      # видно ли машину из сети
ssh root@100.81.197.68             # тот же адрес, что по умолчанию в deploy.sh
cd /opt/mydon-app                  # НЕ /opt/mydon — там инфраструктура MYDON/OS
```

Если `tailscale status` пуст — сначала `tailscale up` на своей машине.

### 2. Посмотреть, что автодеплой уже сделал

```bash
git log --oneline -3                                  # на каком коммите сервер
journalctl -u mydon-autodeploy -n 30 --no-pager       # чем кончился последний тик
systemctl list-timers mydon-autodeploy --no-pager     # когда следующий (тик 30 с)
```

Строка `деплой ok: <sha>` означает, что код уже на сервере и здоровье проверено.
Ждать нечего — переходить к шагу 3. Строка `ОШИБКА` означает, что контейнеры
переключены, а health не поднялся: смотреть `docker logs --tail 50 mydon-core`
до того, как что-то менять дальше.

Если сервер отстал от `main` и таймер молчит — запустить деплой руками:

```bash
systemctl start mydon-autodeploy.service && journalctl -u mydon-autodeploy -f
```

### 3. Дописать переменные, которых у сервера ещё нет

Автодеплой их не принесёт (см. выше). Сверять `.env` с `.env.example`:

```bash
comm -23 \
  <(grep -oE '^[A-Z_]+=' .env.example | sort -u) \
  <(grep -oE '^[A-Z_]+=' .env         | sort -u)
```

Вывод — имена переменных, которых в боевом `.env` нет. Для полевого контура
(PR #111) их четыре, и все четыре дописываются так:

```bash
cp .env .env.bak.$(date +%F)                      # откатиться будет чем

# Перец приглашений. Генерируется ЗДЕСЬ, как остальные секреты. Пустой перец
# Core не роняет осознанно — поэтому пропажа тихая: приглашения хешировались
# бы без перца. Менять позже нельзя: смена гасит все ВЫДАННЫЕ приглашения.
grep -q '^INVITE_PEPPER=.' .env || printf 'INVITE_PEPPER=%s\n' "$(openssl rand -hex 32)" >> .env

# Привязка сотрудника по @username. Ник в Telegram освобождается после смены,
# и занявший его получит чужую карточку. Ставим "0": штатный путь — приглашение.
# Цена решения: сотрудник, чья карточка заведена с ником, но ещё не связана с
# Telegram, без приглашения не войдёт. Это и есть намерение, а не побочный эффект.
grep -q '^STAFF_LINK_BY_USERNAME=' .env || echo 'STAFF_LINK_BY_USERNAME=0' >> .env

# Имя бота без @ — панель собирает из него ссылку-приглашение.
grep -q '^TELEGRAM_BOT_USERNAME=.' .env || echo 'TELEGRAM_BOT_USERNAME=<имя_бота>' >> .env

# Монитор графиков: 06:00, ДО дайджеста сотрудникам (07:00).
grep -q '^MAINTENANCE_MONITOR_CRON=' .env || echo 'MAINTENANCE_MONITOR_CRON=0 6 * * *' >> .env

chmod 600 .env
grep -c '^[A-Z_]*=' .env        # столько строк стало — значения не печатаем
```

**Сбор Ourvend.** Отдельно, потому что требует учётной записи кабинета:

```bash
grep -q '^OURVEND_ACCOUNT=.' .env || echo 'OURVEND_ACCOUNT=<логин кабинета>' >> .env
grep -q '^OURVEND_PASSWORD=.' .env || echo 'OURVEND_PASSWORD=<пароль>' >> .env
grep -q '^OURVEND_SYNC_CRON=' .env || echo 'OURVEND_SYNC_CRON=0 */3 * * *' >> .env
# Сколько ждать ответа Core на приём (слоты, продажи, детектор заливок,
# учётный снапшот), мс. По умолчанию 60000; поднимать, если в логе агентов
# «приём слотов N мс» подполз к этому потолку — парк вырос или база отвечает
# медленнее. При 10 000 сбор падал каждые три часа «This operation was
# aborted» с machines_ok=0 (24.08.2026).
grep -q '^CORE_INGEST_TIMEOUT_MS=' .env || echo 'CORE_INGEST_TIMEOUT_MS=60000' >> .env
```

Без учётки сбор молча выключен: `machine_slot` не обновляется, `slot_snapshot`
не пишется. Проверить после шага 4 —
`docker logs mydon-agents 2>&1 | grep -i вендинг` должно сказать «Сбор вендинга
включён», а не «выключен».

`TELEGRAM_BOT_USERNAME` — единственная, куда надо вписать значение руками
(имя бота без `@`). Остальные три самодостаточны.

**`SYNC_STALE_HOURS` (П8a) — НЕ переменная `.env`.** Порог застоя сбора
OurVend (по умолчанию 6 ч — сбор ходит раз в 3 часа, 6 ч = два пропущенных
прогона подряд) живёт в панельных «Настройках» (`system_config`, ключ
читается `readIntSetting`, база важнее env) — трогать в панели «Система»,
без рестарта. В список переменных `.env` этого шага он не входит; здесь —
для полноты карты ключей П8a.

### 4. Перезапустить то, что читает изменившиеся переменные

`docker compose` перечисляет окружение явно, поэтому новые значения попадают
в контейнер только при пересоздании. Рестарт (`restart`) не годится — он
оставляет старое окружение.

```bash
docker compose -f deploy/docker-compose.yml --env-file .env up -d \
  mydon-core mydon-cc mydon-bot mydon-agents
```

### 5. Проверить

```bash
docker ps --filter name=mydon- --format '{{.Names}}: {{.Status}}'
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node -e 'fetch("http://127.0.0.1:3001/health").then(r=>r.json()).then(d=>console.log(d))'

# Перец доехал? Печатаем длину, а не значение.
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node -e 'console.log("INVITE_PEPPER length:", (process.env.INVITE_PEPPER||"").length)'

docker logs --tail 20 mydon-bot      # «MYDON Bot запущен»
docker logs --tail 20 mydon-agents   # среди мониторов — монитор графиков
```

Длина перца `0` означает, что шаг 3 или 4 не сработал: возвращаться к ним,
дальше не идти.

**Сбор OurVend — первая точка диагностики.** Если числа в отчётах старые или
пустые, смотреть НЕ в логи агентов, а в `GET /ourvend/health`: там серия
отказов подряд, момент последнего успеха, возраст снимков (слоты · продажи ·
продажи по товарам) и паритет с учётной дорожкой. Ровно это показывают панель
(«Снек» → «Здоровье сбора») и бот (команда «сверка»), и ровно этого не хватало
24–25.08.2026, когда сбор падал 12 раз подряд и смотреть было некуда.

```bash
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node -e 'fetch("http://127.0.0.1:3001/ourvend/health?runs=20").then(r=>r.json()).then(d=>console.log("отказов подряд:", d.failedStreak, "| последний успех:", d.lastSuccessAt, "| застой, ч:", d.staleHours, "/ порог", d.staleThresholdH, "| лаг слотов, мин:", d.slotsLagMin, "| лаг продаж, ч:", d.salesLagH))'
```

`failedStreak ≥ 3` — сбор стоит (об этом же приходит тревога
`ourvend.sync_failed_streak`); `lastSuccessAt` давний при нулевой серии
означает, что сбор перестал ЗАПУСКАТЬСЯ — смотреть таймеры агентов, новых
отказов в журнале не будет. `slotsLagMin`/`salesLagH` равны `null` — снимков
нет вовсе, а не «свежие».

**`staleHours`/`staleThresholdH` (П8a) — другой сторож, другая дыра.**
`failedStreak` ловит явные `failed`; он не сработает, если коллектор вообще
не запускается (контейнер агентов лёг, крон не встал) — тогда `failed` в
журнале тоже нет. `staleHours` считает часы с последнего УСПЕШНОГО прогона
независимо от того, были ли отказы; «успешным» здесь считается и
`status='success'`, и `status='partial'` (волна фиксов, R-FW-P4 — частичный
сбор означает, что коллектор жив и данные приехали, пусть не все; только
`failedStreak` продолжает считать исключительно `failed`, эти два счётчика
ловят разное и путать их нельзя). `null` значит «успешных прогонов не
было вовсе» (это тревожнее нуля часов, а не «недавно собрали» — читать как
ноль нельзя). `staleThresholdH` — тот же порог, что в `SYNC_STALE_HOURS`,
едет в ответе, чтобы бот и панель сравнивали с базой, а не со своей копией
константы. `staleHours ≥ staleThresholdH` (каждые 30 мин, крон
`SyncStaleService`) — событие `ourvend.sync_stale`, дедуп раз в ташкентские
сутки, доставка `immediate`; та же цифра видна ботом («сверка») и панелью
(«Здоровье сбора»).

### 6. Завести нормативы обслуживания

Без них раздел «Графики» пуст: система знает, как считать срок, и не знает,
от чего. Числа владельца уже в коде — команда раскладывает их на весь парк,
различая типы автоматов: кофейным (привязанным к кофейной точке) мойка миксера
раз в 10 дней и фильтр воды раз в 45, **всем** — плановое ТО раз в 90. Снеку
мойка миксера не заводится: у него нет ни миксера, ни фильтра, и такой график
краснел бы за работу, которой не существует. Идемпотентно, правки владельца
по отдельным автоматам переживает.

```bash
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node tools/apply-maintenance-norms.mjs --dry-run    # посмотреть, что будет
docker compose -f deploy/docker-compose.yml --env-file .env exec -T mydon-core \
  node tools/apply-maintenance-norms.mjs              # завести
```

Проверить: панель → **Обслуживание** → раздел «Графики». Все строки должны быть
🟢 с датой через 10/45/90 дней, а не 🔴: сроки считаются от дня заведения.

### 7. Подключить сотрудников

Приглашение одноразовое, действует 24 часа (`INVITE_TTL_HOURS`), гасится
первым входом. Выдаётся в панели: **Команда** → карточка человека → блок
«Доступ» → «Выдать ссылку для входа»; ссылка показывается **один раз**. Тот же
путь есть у владельца в боте.

Ссылка вида `https://t.me/<бот>?start=inv_…` отправляется человеку **лично**.
В группу нельзя: первый, кто её откроет, и станет этим сотрудником.

После входа проверить в боте у самого сотрудника: `/start` → внизу экрана
постоянное меню, «📋 Мои задачи» отвечает списком, «🗓 Графики» — тем, что
завёл шаг 6.
