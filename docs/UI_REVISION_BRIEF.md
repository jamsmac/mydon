# ТЗ: пересмотр интерфейса оболочки (apps/cc)

Дата: 2026-08-01. Основание — обратная связь владельца: «переходишь с одной
страницы на другую внутри Источников — выкидывает наверх, приходится опять
листать вниз; хочется удобнее разложить страницы и, может, объединить —
например, Источники внутри Отчётов».

Задача: пересмотреть навигацию и раскладку экранов целиком и применить лучшее
решение, не ломая уже работающую логику (данные, утверждение, срезы).

---

## Коротко

Три беды, все из одного корня — **навигация построена на полных переходах по
URL, а прокрутка живёт в одном длинном контейнере**:

1. **Прокрутка сбрасывается наверх** при каждом переключении под-вкладки, отчёта
   или режима. Причина техническая и точечная (см. §2.1).
2. **Три уровня вкладок через query-параметры** (`?tab=`, `mode/src/rep`) —
   глубоко, легко потеряться, «где я» не читается с одного взгляда.
3. **Доменная страница — монолит** (`domain/[domain]/page.tsx`, ~530 строк):
   все вкладки собираются одним серверным компонентом, поэтому каждый клик —
   полный round-trip к Core и повторная отрисовка всего.

Плюс смысловая рыхлость IA: **Источники и Отчёты разведены**, хотя отчёты
строятся на данных источников; **две очереди утверждения** («Решения» для
агентов и «На утверждение» для реестра) стоят в разных местах.

---

## 1. Текущая структура (инвентаризация)

### Оболочка (layout)
`header` · `Sidebar` (десктоп) / `TabBar` (телефон) · `main.scroll` · `FloatingChat`.
Единственный прокручиваемый контейнер — `main.scroll`
(`globals.css:95`: `flex:1; overflow-y:auto`). Вся страница крутится в нём.

### Уровни навигации
- **L1 — верхнее меню** (`nav.tsx`): Главное, Задачи, Решения, Команда, Агенты,
  направления (GLOBERENT/VendHub/…), Реестр, Журнал, На утверждение. 9+ пунктов.
- **L2 — вкладки домена** (`domain/[domain]/page.tsx`): `.tabs` (Дашборд, группы
  каталога, Инкассация, Источники, Команда, Задачи) + `.subtabs` (листья группы).
  Всё через `href = /domain/${d}?tab=...` — полные навигации.
- **L3 — внутри Источников** (`sources-view.tsx`): выбор источника (`src`),
  выбор отчёта (`rep`), режим (`mode`: сверка/объединённый/все продажи). Тоже
  query-параметры, тоже полные навигации.

### Маршруты (страницы)
`/` `/mydon` `/tasks` `/tasks/[id]` `/approvals` `/team` `/team/[id]` `/agents`
`/agents/[name]` `/domain/[domain]` `/registry` `/card/[id]` `/audit` `/queue`
`/assistant`.

## 2. Проблемы и причины

### 2.1 Прокрутку сбрасывает наверх (P0 — главная боль)
`next/link` по умолчанию делает `scroll={true}`: при навигации окно
прокручивается в начало. **Ни в одном `<Link>` оболочки нет `scroll={false}`**
(проверено). Поэтому любой клик по под-вкладке/отчёту/режиму, находящемуся внизу
длинной страницы, возвращает пользователя наверх — и он листает заново.

Особенно бьёт по Источникам: список отчётов и таблица данных — далеко внизу;
переключил отчёт → оказался наверху → листай вниз опять.

### 2.2 Глубина и «где я» (P1)
Три уровня вкладок, все на query-параметрах, без «хлебных крошек» и без
устойчивого якоря положения. Активное состояние читается только по подсветке
вкладок, а их два-три ряда.

### 2.3 Монолит доменной страницы (P1)
`domain/[domain]/page.tsx` грузит данные ВСЕХ вкладок (обязательства, продажи,
инкассация, реестр, задачи, команда) и рендерит выбранную. Переключение вкладки
= новый серверный запрос всего. Медленно и мешает независимой прокрутке.

### 2.4 Смысловая рыхлость (P2)
- **Источники ↔ Отчёты**: отчёты (журнал, цены, товары, оплата, сверки) —
  это срезы поверх данных источника. Сейчас они в разных местах; связь «откуда
  цифра» приходится держать в голове.
- **Две очереди**: `/approvals` (предложения агентов) и `/queue` (черновики
  реестра). Обе — «что ждёт моего слова», но в разных разделах меню.
- Карточка (`/card/[id]`) — длинный вертикальный свиток из 6–9 секций без
  внутренней навигации.

## 3. Принципы редизайна

1. **Положение не теряется.** Переключение под-раздела не двигает прокрутку.
   URL-состояние сохраняем (шаринг, «назад»), но без скачка наверх.
2. **Панель управления всегда на виду.** То, чем переключаешь (вкладки, выбор
   отчёта), — «липкое» (sticky), контент под ним прокручивается сам.
3. **Не глубже двух уровней вкладок** в поле зрения одновременно; третий уровень
   — внутри рабочей области, а не ещё одним рядом сверху.
4. **Одна оболочка — много движков** (принцип проекта): объединяем то, что
   логически одно, но не сливаем разные движки в одну кашу.
5. **Данные грузим по надобности.** Вкладка тянет только своё.
6. **Ничего не ломаем в логике.** Меняем раскладку и навигацию, а срезы,
   утверждение и записи Core остаются как есть.

## 4. Целевая структура (IA) — УТВЕРЖДЕНО владельцем 2026-08-01

### 4.0 Карта интерфейса (для утверждения)

```
Меню (L1)
├─ Главное
├─ Входящие ← объединяет «Решения» (агенты) + «Новые карточки/значения» (реестр)
├─ Задачи
├─ Команда
├─ Агенты
├─ Направления: GLOBERENT · VendHub · (Личное — только владелец)
├─ Реестр
└─ Журнал

Внутри направления VendHub (вкладки, L2)
├─ Дашборд
├─ Каталог (товары · ингредиенты · автоматы · склады …)
├─ Отчёты ← бывш. «Источники», большой раздел, раскладка мастер-деталь
│   └─ Источник (gjvending · OurVend …)
│        └─ его Отчёты (Order Query · Operating …)
│             └─ Срез (Строки · Журнал · Цены · Товары · Оплата · Сверки)
├─ Инкассация
├─ Команда
└─ Задачи

Карточка (/card) — с липким оглавлением секций.
```

### 4.1 Раздел «Отчёты»: источник → его отчёты → срез (РЕШЕНО)
Отчёты и Источники — **одно целое, не разделять**. Слово владельца: «отчёты —
то, ради чего смотришь; они исходят из источников; у каждого источника свои,
разные отчёты». Поэтому раздел один, а дерево — **источник содержит свои
отчёты, отчёт содержит свои срезы**:

```
Отчёты (в домене VendHub)
├─ Источник: gjvending
│   ├─ Отчёт: Order Query
│   │   ├─ Строки (сырьё) · Журнал продаж
│   │   ├─ Цены · Товары · Оплата
│   │   └─ Сверки (с другим отчётом)
│   └─ Отчёт: …
└─ Источник: OurVend → …
```

Раскладка **мастер-деталь**: липкая панель выбора (источник → отчёт → срез)
сверху/слева; рабочая область (таблица/журнал/сверка) — справа/снизу,
прокручивается независимо. Название раздела в меню домена — «Отчёты» (ведёт
то, ради чего смотрят); источник — организующий слой внутри.

### 4.2 Свести две очереди в один «Входящие» (РЕШЕНО — на усмотрение исполнителя)
`/approvals` (агенты) и `/queue` (реестр) — оба «ждёт моего слова». Сводим под
один пункт меню **«Входящие»** с двумя секциями: «Решения агентов» и «Новые
карточки/значения». Один значок-счётчик = суммарное ожидание. Экраны и логика
уже есть — объединяем ВХОД, механику не переписываем.

### 4.3 Доменную страницу — на под-сегменты
Разбить монолит `domain/[domain]/page.tsx` на сегменты App Router
(`/domain/[domain]/(tabs)/overview`, `/reports`, `/catalog/[type]`, `/collect`,
…) или клиентские вкладки с сохранением URL — чтобы каждая грузила только своё
и переключалась без полной перерисовки.

### 4.4 Карточку — с оглавлением
Липкое мини-оглавление секций («Утверждение · Фото · Где стоит · Рецепт ·
Склад») с плавным скроллом к секции; на широком экране — как боковая колонка.

## 5. Технические решения

### 5.1 Быстрая победа: не прыгать наверх (P0, ~1–2 ч)
- Проставить `scroll={false}` всем под-навигационным `<Link>` (вкладки домена,
  под-вкладки, выбор источника/отчёта/режима в `sources-view`, переходы каталога
  внутри вкладки). Для внешних переходов (смена раздела L1) прокрутку наверх
  оставляем — там это уместно.
- Проверить: переключение отчёта/режима держит позицию; «назад» её
  восстанавливает (в App Router восстановление скролла работает, если навигация
  не форсит `scroll=true`).

### 5.2 Липкая панель управления
- Ряд вкладок/выбор отчёта — в `position: sticky; top: 0` внутри `main.scroll`,
  с фоном оболочки, чтобы контент уезжал под неё, а не толкал её.
- Рабочая область данных получает свой `overflow` при необходимости (широкие
  таблицы уже скроллятся горизонтально — сохранить).

### 5.3 Разбиение монолита
- Перевести вкладки домена на **сегменты маршрута** с общим `layout.tsx`
  (липкие вкладки живут в layout, контент — в сегменте). Это даёт независимую
  загрузку, встроенное сохранение позиции и чистые URL без `?tab=`.
- Либо, как промежуточный шаг, вынести тяжёлые вкладки в отдельные клиентские
  компоненты с ленивой загрузкой их данных.

### 5.4 Сохранение позиции при «назад»
- Опираться на встроенное восстановление скролла App Router (не форсить scroll).
- Для мастер-деталь Источников — держать состояние выбора в URL, положение
  списка отчётов не сбрасывать при выборе отчёта.

## 6. По экранам: что меняем

| Экран | Сейчас | Становится |
|---|---|---|
| Домен (`/domain`) | монолит, 2 ряда вкладок, полные переходы, скролл наверх | сегменты маршрута, липкие вкладки, `scroll={false}`, ленивые данные |

| Меню (`nav`) | 9+ пунктов, две очереди | сгруппировать, «Входящие» вместо двух |

## 7. Порядок внедрения

- **Фаза 0 (P0, быстро):** `scroll={false}` на под-навигации + липкие панели
  вкладок. Снимает главную боль «выкидывает наверх» без структурных изменений.
- **Фаза 1 (P1):** объединить Источники и Отчёты в раздел «Данные»
  (мастер-деталь), свести две очереди во «Входящие».
- **Фаза 2 (P1):** ленивая загрузка данных доменной страницы.
  СДЕЛАНО как ленивая загрузка НА МЕСТЕ (без миграции URL): обязательства и
  сводки продаж/склада тянутся только на дашборде, переключение вкладки больше
  не запрашивает данные всех разделов. Полный переход на сегменты маршрута
  (`?tab=` → `/vendhub/reports`) сознательно НЕ делаем: он ломает дрилл-ссылки,
  ⌘K и хлебные крошки по всему приложению ради малого выигрыша, а развилка §9.3
  (сегменты против вкладок) владельцем не выбрана. Липкий layout уже дала Фаза 0.
- **Фаза 3 (P2):** оглавление карточки, полировка меню, единый ритм отступов.

Каждая фаза — отдельный PR, ничего не ломает: сначала UX-скачок (Фаза 0), потом
структура. Логика Core, срезы и утверждение не трогаются.

---

## 8. Критерии приёмки

- Переключение под-вкладки/отчёта/режима **не двигает** прокрутку; «назад»
  возвращает на прежнее место.
- «Где я» читается с одного взгляда: активный источник/отчёт/срез виден без
  прокрутки (липкая панель).
- Отчёты открываются из своего источника, «откуда цифра» — по месту, а не в
  другом разделе.
- Один вход «Входящие» с суммарным счётчиком ожидания.
- Ни один существующий срез/запись/утверждение не изменил поведение
  (тесты Core/shared/bot остаются зелёными).

   (рекомендуется) — или наоборот, срезы верхнего уровня, а источник — фильтр?
2. **Очереди:** сливать «Решения» и «Новые карточки» в один экран с секциями
   (рекомендуется) — или оставить два пункта, но рядом в меню?
3. **Доменные вкладки:** сегменты маршрута (чище URL, больше работы) — или
   клиентские вкладки с сохранением `?tab=` (быстрее внедрить)?
