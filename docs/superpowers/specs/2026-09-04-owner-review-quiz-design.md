# Режим «Ревизия» — квиз владельца над всем, что ждёт его слова

Дата: 2026-09-04
Статус: спека; первый проход уже идёт вне системы (артефакт «Ревизия MYDON»), вторая фаза — режим внутри панели и бота
Связано: `2026-08-26-p7-tasks-design.md` (подтверждение задач), `2026-08-31-p5-web-identity-rbac-design.md` (owner-действия),
`2026-09-04-llm-skill-executor-design.md` (гейт активации агентов). Цитаты строк — по `main` @ d059ef8.

## Цель

Владелец решает вопросы **по одному**, а не списками: один пункт на экран, четыре действия — Подтвердить ·
Изменить · Удалить · Пропустить, — сгруппировано по разделам, решённое исчезает, пропущенное возвращается в
конце раздела. Черновики (описания, миссии, границы, значения полей) заполняют агенты и Claude; владелец
подтверждает или правит. Агенты переводятся в `active` **постепенно**: только после того, как их паспорт пройден
целиком.

Сегодня всё, что ждёт слова владельца, уже собрано во Входящих (`apps/cc/src/app/inbox/page.tsx`): решения
агентов (`approval`), новые карточки реестра (`entity.approvedAt IS NULL`), предложенные значения полей
(`entity_draft`). Но это **списки с кнопками**, а не последовательность; настройки агентов (`agent`) и страницы
знаний в очередь не попадают вовсе; «пропустить» нет — пункт либо решается, либо висит. Режим «Ревизия» —
новая *подача* поверх существующих примитивов, плюс три недостающих источника и снооз.

## Инварианты

- **R-RV-1 Ревизия — подача, не новая истина.** Каждое действие квиза вызывает **существующий** эндпоинт
  (таблица выше). Новых способов «утвердить» не появляется; аудит остаётся тем же.
- **R-RV-2 Четыре действия, одинаковые для всех типов.** Подтвердить · Изменить · Удалить · Пропустить.
  Что они значат для каждого типа пункта — таблица §«Типы пунктов». Недоступное действие для типа **скрыто**,
  не задизейблено (например, «Удалить» у предложения агента = «Отклонить», у поля паспорта агента — отсутствует).
- **R-RV-3 Пропустить = снооз, не решение.** Пункт получает `review_snooze.until` (по умолчанию +24 ч) и
  возвращается в конец своего раздела; в счётчиках он остаётся «нерешённым». Снооз — единственное новое
  состояние; хранится в Core, чтобы телефон и компьютер видели одно и то же.
- **R-RV-4 Группа = задача.** Для каждого раздела с нерешёнными пунктами Core держит задачу
  `Ревизия · <раздел>` (source key `review:<раздел>`, тот же частичный индекс `task_source_key`, что у авто-задач
  П7); описание — счётчик «N из M», обновляется при каждом решении; при N = 0 задача закрывается сама (`done`,
  `closed_by: system`). Так ревизия видна в `/tasks`, в брифинге 07:30 и в Telegram, а «убирать по мере решения»
  происходит само.
- **R-RV-5 Порядок детерминирован.** Внутри раздела — по `createdAt` источника, снооз — в конец по `until`.
  Владелец может открыть любой пункт из списка решений и пересмотреть его.
- **R-RV-6 Паспорт агента — поле за полем, с хэшем.** Таблица `agent_field_review (agent_id, field, value_hash,
  reviewed_at, reviewed_by)`; поле считается пройденным, пока `value_hash` совпадает с текущим значением. Любая
  правка поля (панель, сид, агент) меняет хэш → поле снова в очереди. Поля: `status`, `autonomyDefault`,
  `description`, `mission`, `nonGoals`, `skills`, `schedule`, `budgetPerDayUsd`+`budgetOnExceeded`, `kbPages`
  (после спеки llm-skill), `breakGlass`, `webSources`, `ideaChannels`.
- **R-RV-7 Гейт активации.** `PATCH /agents/:name` со `status: active` принимается, только если у агента нет
  непройденных полей (R-RV-6) — иначе `409` со списком полей. Обход — только владельцем и явно:
  `{ status: "active", force: true }` под `OwnerMutationGuard`, с событием `agent.activated_unreviewed` в аудит.
  Постепенность включения — следствие: агент включается тогда, когда его раздел ревизии закрыт.
- **R-RV-8 Черновики заполняет система, решает владелец.** Пустое обязательное поле паспорта (`mission`,
  `nonGoals` — их требует `check-passports`) попадает в очередь **с предложением**: черновик пишет
  `knowledge-curator` (навык `kb-review` расширяется на паспорта) или Claude при переносе; пункт без черновика
  допустим, но помечается «черновика нет».
- **R-RV-9 Только владелец.** Экран `/review` и команда бота — за owner-guard (R-P5-8/9); сотрудникам ревизия
  не показывается. Личный контур — как везде: пункты домена `personal` видит только владелец.
- **R-RV-10 Ничего не теряется при отмене.** Решение по карточке реестра или полю необратимо ровно так же,
  как сегодняшняя кнопка (отклонённое поле уходит без следа — это уже принятое поведение); квиз показывает
  «Точно удалить?» вторым нажатием и никогда не удаляет по клавише без подтверждения.

## Типы пунктов и что значат действия

| Тип пункта | Источник | Подтвердить | Изменить | Удалить | Пропустить |
|---|---|---|---|---|---|
| Новая карточка реестра | `entity.approvedAt IS NULL` | `approve` | форма карточки → `PATCH` + `approve` | `DELETE /entities/:id` (второе нажатие) | снооз |
| Предложенное значение поля | `entity_draft` | `approve-field` | своё значение → `propose` + `approve-field` | `reject-field` | снооз |
| Предложение агента | `approval.status = pending` | `decide: approve` | комментарий владельца + `approve` (комментарий — в `note`) | `decide: reject` | снооз |
| Поле паспорта агента | `agent` × `agent_field_review` (хэш не совпадает / нет записи) | записать review с текущим хэшем | `PATCH /agents/:name` (или `/autonomy`) + review | — (скрыто; удаление навыка/расписания — это «Изменить» списка) | снооз |
| Страница знаний с пометкой | предложения `knowledge-curator/kb-review` как `approval` с `kind: kb` | approve → curator применяет diff | правка текста предложения + approve | reject | снооз |
| Задача ждёт подтверждения | `task.awaiting` (П7) | `confirm` | «вернуть в работу» с причиной (существующий маршрут П7) | — | снооз |

Разделы (группы) первой версии: по одному на агента («Агент globerent-sales»), «Реестр · <тип карточки>»
(автоматы, контрагенты, договоры…), «Предложения агентов», «База знаний», «Задачи на подтверждение».

## Экран `/review` (панель)

Один пункт на экран, как в артефакте первого прохода: сверху раздел и позиция «7 из 13 · решено 4», карточка —
заголовок · блок «Сейчас» · блок «Предлагаю» (если есть черновик) · подсказка · источник; снизу — фиксированная
панель четырёх действий (на телефоне 2×2, на компьютере в ряд с клавишами 1–4). «Изменить» открывает лист с
подсказками-чипами и полем. После действия — следующий пункт раздела; раздел закрыт → сводка и «Дальше ·
<следующий раздел>». Обзор — список разделов с прогрессом и кнопкой «Продолжить». Список решений — с фильтром и
возможностью открыть пункт заново. Дизайн — токены и примитивы `mydon-design` (`.card`, `.eyebrow`, `.pill`,
`.btn.pri` — оранжевая заливка с тёмными чернилами; аватар агента — `.av8`).

Вход: пункт меню «Входящие» получает вторую кнопку «Пройти по одному» (`/review`); главная — виджет
«Ревизия: осталось N» → `/review`.

## Telegram

Команда `/ревизия` (owner-only): бот шлёт пункт текстом (раздел, заголовок, «Сейчас», «Предлагаю») и inline-кнопки
✅ Подтвердить · ✏️ Изменить · 🗑 Удалить · ⏭ Пропустить; «Изменить» → бот просит ответить текстом (следующее
сообщение владельца = новое значение), «Удалить» → второе подтверждение. Механика callback — существующая
(`index.ts:1002-1078`), тексты решений — те же, что в панели. После действия бот сразу шлёт следующий пункт;
«Стоп» — выйти.

## Данные

- `review_snooze (item_key text pk, until timestamptz, by text, created_at)` — `item_key` = `<тип>:<id>[:<поле>]`.
- `agent_field_review (agent_id uuid, field text, value_hash text, reviewed_at, reviewed_by, pk (agent_id, field))`.
- Read model `GET /review/queue` в Core: объединяет источники таблицы выше, считает разделы и порядок (R-RV-5),
  отдаёт `{ groups: [{ key, title, total, done, items: [...] }] }`; пункты — с `current`, `proposal`,
  `actions` (какие доступны), `itemKey`. Панель и бот читают один и тот же ответ.
- Задачи-группы (R-RV-4) создаёт и обновляет `ReviewService` внутри Core вызовом `TasksService.ensureForDay`
  (метод, не HTTP — правило R-P7-7), закрывает при нуле.

## Первый проход и мост к системе

Первый проход уже выполняется **вне системы** — артефакт «Ревизия MYDON» (149 пунктов: 12 паспортов агентов и
14 страниц знаний, черновики заполнены). Его решения хранятся в базе артефакта (`decisions/<id>`, `id` вида
`A.<agent>.<field>` / `B.kb.<page>`) и применяются так:

1. Паспорта — через Core (`PATCH /agents/:name`, `/autonomy`) и зеркально в `config.yaml` (сид), одним PR
   `chore/review-pass-1`; каждое применённое поле получает запись `agent_field_review` с хэшем — так первый проход
   не повторяется в системе.
2. KB — правки страниц и `kb/index.md` тем же PR; страницы с решением «удалить» убираются из `kb_pages` агентов.
3. Инструмент `tools/import-review-decisions.mjs` читает экспорт решений (JSON) и генерирует патчи + список
   `agent_field_review` — чтобы перенос был проверяемым, а не ручным.

## Явные границы этой фазы

- Не меняются семантика approve/reject/approve-field, аудит, ledger, тиры.
- Нет массовых действий в квизе («утвердить всё») — они остаются во Входящих списком (`approveAllCards`).
- Нет ревизии для сотрудников и ролей — только владелец.
- Страницы KB попадают в очередь только через предложения `knowledge-curator` (файлы образа Core не читает).
- Порядок разделов фиксированный (агенты → реестр → предложения → KB → задачи); настраиваемый порядок — позже.

## Приёмка

1. Владелец с телефона открывает `/review`, проходит раздел «Агент globerent-sales» до конца: 13 пунктов, каждый
   решён одним из четырёх действий; задача `Ревизия · Агент globerent-sales` закрылась сама; в `agent_field_review`
   — 12 записей с хэшами.
2. `PATCH /agents/globerent-sales {status: active}` до прохождения → `409` со списком полей; после — `200`.
3. Правка `mission` из панели → поле снова в очереди (хэш разошёлся), задача-группа открылась заново с «1 из 13».
4. «Пропустить» на телефоне → пункт исчез и появился в конце раздела на компьютере без перезагрузки (снооз в Core).
5. В Telegram `/ревизия` показывает тот же следующий пункт, что и панель; ✅ в боте убирает его из панели.
6. Решение по предложению агента через квиз оставляет в аудите ровно ту же запись, что кнопка во Входящих.
7. Импорт решений первого прохода (`tools/import-review-decisions.mjs`) даёт diff `config.yaml`/KB и заполняет
   `agent_field_review`; повторный запуск идемпотентен.

## Выкатка

PR 1 — Core: `review_snooze`, `agent_field_review`, `GET /review/queue`, гейт активации (R-RV-7), задачи-группы.
PR 2 — панель `/review` + виджет на главной. PR 3 — бот `/ревизия`. PR 4 — `kb-review` расширяется на паспорта
(черновики миссий/границ). Откат: экран и команда убираются без миграций; таблицы обратно-совместимы; гейт
активации отключается настройкой `REVIEW_ACTIVATION_GATE=0` (в `config-spec.ts`, база важнее env).
