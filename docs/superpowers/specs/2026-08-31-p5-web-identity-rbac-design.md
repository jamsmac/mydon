# Пункт 5 аудита: web identity + RBAC + разделение SERVICE_TOKEN (дизайн)

> Дата: 2026-08-31. Не порт — дизайн-срез. Требует решений владельца (раздел 4).
> Основание: аудит Codex 31.08 (P0 «web-аутентификация и owner-only RBAC
> отсутствуют»); подтверждено инвентаризацией на текущем main.

## 1. Что есть сейчас (инвентаризация, факты)

- **CC (панель)** привязана прямо к Tailscale-IP: `PANEL_BIND=<tailscale-ip>`,
  порт 3002. НЕ за `tailscale serve` → per-request identity-заголовков
  (`Tailscale-User-Login`) нет. Middleware/login/session в `apps/cc/src` нет
  вовсе. Единственная граница — сам факт нахождения в tailnet. Любое
  устройство/узел в tailnet, дотянувшееся до :3002, имеет ПОЛНЫЙ доступ к
  панели, включая `/domain/personal`.
- **Core**: `ServiceTokenGuard` требует `x-service-token` на мутациях
  (POST/PATCH/PUT/DELETE), fail-closed без токена. GET открыты полностью
  (осознанно: «панель и бот читают много, вреда от чтения в закрытой сети
  нет») — включая чтение личного контура.
- **SERVICE_TOKEN общий** у CC, Bot, Agents (`apps/cc/src/lib/core.ts:35`,
  `apps/bot/src/index.ts:77`, `apps/agents/src/index.ts:152`). Один секрет —
  ни различить источник мутации, ни отозвать по сервису нельзя. Approval,
  роли, `AGENT_AUTONOMY_MAX` защищены ровно этим общим токеном.
- **OWNER_ACTION_TOKEN** + `OwnerActionGuard` (`x-owner-action-token`, обязан
  отличаться от SERVICE_TOKEN) уже существуют, но применены в ОДНОМ месте —
  `tasks.controller.ts:692` (снятие LLM replay-блока). Это готовый «второй
  пояс» для необратимых действий владельца, просто почти не используется.

## 2. Дыры (по убыванию серьёзности)

1. **[P0] Личный контур виден анониму на tailnet.** GET `/domain/personal`
   и его Core-эндпоинты отдаются без какой-либо проверки, кто смотрит.
   Только Tailscale отделяет их от «любого узла в сети».
2. **[P0] Нет разделения identity сервисов.** Общий SERVICE_TOKEN = CC, Bot и
   Agents неотличимы для Core. Скомпрометированный любой из трёх = полный
   доступ на запись; отозвать один, не сломав остальные, нельзя.
3. **[P1] Owner-only действия защищены общим токеном.** Approvals, смена
   ролей, порог автономии сейчас под ServiceTokenGuard (общий токен), а не под
   OwnerActionGuard — их может провести любой держатель SERVICE_TOKEN (в т.ч.
   сам Agents-worker), что противоречит модели «владелец жмёт руками».

## 3. Предлагаемый минимально-достаточный срез (MVP)

Полный RBAC/SSO — большой проект. MVP закрывает три дыры, не переусложняя:

- **(A) Личный контур за identity.** GET личного контура (CC-роут + Core-
  эндпоинты домена `personal`) закрыть: Core перестаёт отдавать `personal`
  без owner-identity; CC-роут `/domain/personal` требует владельца.
- **(B) Owner-identity в CC.** Ввести на уровне панели понятие «кто смотрит»,
  чтобы (A) имело смысл и чтобы owner-only действия шли под owner-identity, а
  не под общим токеном.
- **(C) Owner-only мутации под OwnerActionGuard.** Approvals-решения, смена
  ролей, `AGENT_AUTONOMY_MAX` перевести со ServiceTokenGuard на второй пояс
  (OwnerActionGuard / owner-identity). Механика уже есть — расширить охват.
- **(D) [опционально, может быть follow-up] Разделение SERVICE_TOKEN** на
  per-service (CC/Bot/Agents), чтобы Core различал источник и отзыв был
  точечным.

## 4. Развилки для владельца (нужны решения ДО реализации)

### Р-1. Механизм identity панели (как панель узнаёт, что смотрит владелец)
- **(а) Tailscale serve + identity-заголовки** — перевести CC за
  `tailscale serve`; Tailscale уже аутентифицирует узел/пользователя и
  проставляет `Tailscale-User-Login`. Панель/Core читают этот заголовок.
  Плюс: ноль паролей, tailnet и так знает, кто ты. Минус: смена схемы
  выставления панели (serve вместо прямого bind), доверие заголовкам только
  из tailnet.
- **(б) Простой app-логин** — пароль/сессия поверх панели (одна учётка
  владельца). Плюс: не зависит от способа сети. Минус: ещё один секрет,
  сессии, куки — то, чего сейчас нет вовсе.
- **(в) Полноценный SSO/OAuth** — избыточно для соло-оператора.
- **Предложение: (а)** — под соло-владельца на Tailscale это самый честный и
  дешёвый путь; identity уже есть в сети, нужно лишь начать её читать.

### Р-2. Глубина разделения SERVICE_TOKEN сейчас
- **(а) Только второй пояс** — оставить общий SERVICE_TOKEN, но owner-only
  мутации (approvals/роли/автономия) увести под OwnerActionGuard (owner-токен
  или owner-identity). Меньше объём, закрывает P1 сразу.
- **(б) Полное per-service разделение** (CC-токен, Bot-токен, Agents-токен со
  скоупами в Core) в этом же срезе. Закрывает P0-2, но крупнее и рискованнее
  (одновременная выкатка секретов на 4 контейнера — есть прецедент боли).
- **Предложение: (а) сейчас, (б) отдельным follow-up** после identity.

### Р-3. Объём среза
- **(а) MVP A+B+C** (личный контур за identity + owner-identity в CC +
  owner-only мутации под второй пояс), D — follow-up.
- **(б) A+B+C+D** всё сразу.
- **Предложение: (а)** — довести до прода безопасно, D отдельно.

## 5. Решения владельца (приняты 2026-08-31)

- **Р-1 → (а)** Tailscale serve + identity-заголовки.
- **Р-2 → (а)** Только второй пояс сейчас; per-service токены — follow-up.
- **Р-3 → (а)** MVP A+B+C; разделение SERVICE_TOKEN (D) — follow-up.

## 6. Рулинги (R-P5-*)

- **R-P5-1 (identity-источник).** Owner-identity Core берёт ТОЛЬКО из заголовка,
  который проставляет `tailscale serve` (`Tailscale-User-Login` — уточнить точное
  имя в текущей версии tailscale на проде). Заголовок из tailnet-фронта; из
  прямого запроса (не через serve) его быть НЕ должно.
- **R-P5-2 (доверять заголовку только от serve).** Core обязан отвергать
  identity-заголовок, если запрос пришёл не через доверенный serve-прокси
  (иначе любой в tailnet подделает заголовок и станет «владельцем»). Механизм:
  serve слушает на loopback/спец-порту, недоступном напрямую; либо общий
  секрет serve↔Core. Это сердце среза — адверсариальное ревью бьёт сюда.
- **R-P5-3 (кто владелец).** «Владелец» = запись person с ролью owner
  (см. память: роль решает `person.roles`, не текстовое поле). Логин из
  заголовка сопоставляется с person по Telegram-/email-/login-идентификатору;
  сопоставление в одном месте (owner-resolver), тестируемо.
- **R-P5-4 (личный контур GET).** Core-эндпоинты домена `personal` и CC-роут
  `/domain/personal` требуют owner-identity. Без неё — не «пусто», а честный
  отказ 403/redirect, не выдающий содержимого. Прочие домены (vendhub,
  globerent, mydon) GET остаются открытыми в tailnet как сейчас (осознанно).
- **R-P5-5 (owner-only мутации под второй пояс).** Approvals-решения, смена
  ролей person, изменение `AGENT_AUTONOMY_MAX`/порога автономии переводятся со
  ServiceTokenGuard на OwnerActionGuard (или owner-identity-эквивалент). CC
  проставляет owner-токен/identity ТОЛЬКО когда действие инициировал владелец —
  не автоматически из общего токена. Bot/Agents этих путей не проходят.
- **R-P5-6 (не запереть владельца).** Выкатка identity — по чек-листу с
  «аварийным входом»: до флипа проверить, что owner-resolver реально узнаёт
  владельца по его tailnet-логину; предусмотреть env-обход (например
  `OWNER_IDENTITY_ENFORCED=0`) на случай, если serve-заголовок не доедет —
  чтобы ошибка конфигурации не отрезала владельца от собственной панели.
- **R-P5-7 (объём).** Per-service разделение SERVICE_TOKEN, RBAC для не-владельцев
  (менеджеры/операторы за пределами Telegram-бота), аудит доступа к personal —
  вне этого среза, follow-up.

## 7. План реализации (SDD по ритуалу)
Волны: инвентаризация (кто рендерит personal в CC, какие Core-эндпоинты у домена
personal, где сейчас approvals/roles/autonomy-мутации) → имплементеры по
непересекающимся файлам (Core: owner-identity middleware/guard + personal-gating
+ перевод owner-only мутаций; CC: owner-resolver из заголовка + гейт роута +
проставление owner-identity в мутациях; deploy: `tailscale serve` вместо прямого
bind + env) → адверсариальное ревью («подделка identity-заголовка из tailnet» +
«владелец заперт снаружи» + конвенции) → волна фиксов → гейт → PR → прод-выкатка
по чек-листу R-P5-6 (env-обход, проверка узнавания владельца, только потом флип).
