## 3. Рулинги

### R-G-1 Единый резолвер каталога: один экспорт, одно правило, явный спор

**Решение.** В `packages/shared/src/stock-history.ts`, рядом с `productIndex`,
появляется ЕДИНСТВЕННАЯ дверь к правилу:

```ts
export type CatalogResolution =
  | { kind: "hit"; canon: string; id: string; source: CanonSource }
  | { kind: "conflict"; raw: string; byName: string; byAlias: string }
  | { kind: "miss"; raw: string };

export function resolveCatalogName(index: Pick<ProductIndex, "explain">, raw: string): CatalogResolution;
```

Приоритет — ТОЧНОЕ имя карточки, потом алиас; сравнение по `normalizeProductName`
(свёртка запятой между цифрами уже там); пустое/пробельное `raw` → `miss`; спор
(«ключ — имя одной карточки и одновременно алиас другой») возвращается ЯВНО.
`canon`/`id` продуктового индекса переписываются через неё, поэтому импорт истории
(`каталог.canon`, `каталог.id`) переиспользует правило БЕЗ единой правки в
`packages/db/src/import-stock-history.ts`. `resolveProductIds` зовёт её напрямую.
`VendingService.loadProductIndex()` строит `productIndex(...)` из ТЕХ ЖЕ двух
выборок и отдаёт его полем `catalog` **вместо** `aliasByKey`;
`resolveProduct(name, catalog)` остаётся тонкой обёрткой ради шестнадцати
вызывающих: `hit → canon`, `conflict → byName` **и `logger.warn`**, `miss → raw`.

**Имя.** Не `resolveProductName`: оно занято донорским мостом
(`stock-history.ts:286`, «своё имя донора → `ourvend_name` → канон»), это ДРУГОЙ
вопрос, и совпадение имён было бы худшим видом путаницы — обе функции про имена
товаров.

**Файл.** В `stock-history.ts`, а не в новом `catalog-resolve.ts`: карты и само
правило (`explain`) живут там, а вынос фасада наружу дал бы модульную пару
«значение туда, типы обратно» ради двадцати строк. Тесты при этом СВОИ
(`catalog-resolve.test.ts`): `stock-history.test.ts` — про донорский импорт, а
это правило теперь исполняет и живой Core.

**Писатели необратимого получают явный результат:**
- `productIdResolver` — `hit → id`, `conflict|miss → null` (сегодня спор молча
  увёл бы строку на карточку алиаса, а `бэкфиллWhere` держит `isNull` — повторный
  прогон это уже не чинит);
- `resolveProductRef` — `conflict → BadRequestException` («имя разрешается двумя
  путями»), `miss → { name: сырое, productId: null }` как раньше; лишний SELECT по
  имени уходит, `id` приезжает из индекса.

**Почему.** Правило одно, а реализаций три, и это уже записано в коде как долг.
На сегодняшнем каталоге расхождение не даёт ни одной разной строки — значит,
момент для унификации максимально дешёвый: цена ошибки измерена и равна нулю, а
через полгода она будет равна количеству новых алиасов.

**Чем платим, если ошиблись.** Обёртка `resolveProduct` ОБЯЗАНА сохранить
`miss → raw`: верни она пустую строку или `null`, и шестнадцать вызывающих начнут
писать в `vending_stock`/`machine_slot` имена, которых нет. Это единственный
способ сломать прод этой задачей, и он закрыт тестом на каждую из трёх веток.

**Доказательство после выкатки.** `backfill-product-ids.js --dry-run` печатает по
цели «История склада (vending_stock_count)» строку `обновилось БЫ 3` — те самые
три имени с «неправильным» разделителем, которые бэкфилл (правило B) привязывает,
а живой резолвер (правило A) не привязывал. Ноль по трём остальным целям — это и
есть «ни одна прод-строка не меняет привязку». Если владелец уже прогнал `--apply`
из чек-листа среза «Хвосты», три строки привязаны и примерка законно покажет `0` —
тогда доказательство читается прямым `SELECT` (у этих трёх строк `product_id`
не `NULL`), а не примеркой.

### R-G-2 Вставка задач ТО: конфликт по `source` С ПРЕДИКАТОМ частичного индекса

**Решение.** `apps/core/src/tasks/tasks.service.ts:388`:

```ts
.onConflictDoNothing({ target: task.source, where: TASK_SOURCE_DAY_PREDICATE })
```

Предикат — ОДНО значение на схему и на вставку: `packages/db/src/schema.ts`
экспортирует `TASK_SOURCE_DAY_PREDICATE`, и `uniqueIndex("task_source_key")`
использует ЕГО ЖЕ. Дословная копия рядом со вставкой разошлась бы с индексом при
первом же уточнении регулярки, а разошедшийся предикат — это тот же `42P10`, но
уже без единого признака в коде.

Дополнительно `EnsureForDayDto.dayKey` получает `@Matches(/^\d{4}-\d{2}-\d{2}$/)`:
`@IsISO8601({strict:true})` пропускает и полную дату-время, а такой `source` не
попадает под предикат индекса — дедуп выключился бы МОЛЧА.

**Почему не `client_key`.** Он существует и он полный UNIQUE, но: (1) его смысл —
ключ идемпотентности КЛИЕНТА (ретрай `POST /tasks`), и на нём уже держится
`create()`; (2) `task_source_key` никуда не денется, и на дубле он ответил бы
`23505` → фильтр отдал бы 400, то есть «дубль» стал бы ошибкой вместо тихого 200;
(3) колонка nullable — пришлось бы дублировать в неё `source`, заведя ВТОРОЙ ключ
на одну и ту же идемпотентность. Вариант «`target + where`» честнее по drizzle:
0.45.2 печатает ровно `on conflict ("source") where <pred> do nothing`
(`insert.cjs:124-134`), а предикат рендерится литералом без единого параметра —
то, что Postgres и требует, чтобы вывести ЧАСТИЧНЫЙ индекс.

**Ответ НЕ меняем.** `ensureForDay` уже возвращает `null` → контроллер отдаёт 200 с
пустым телом → `core-client` читает это как `{ created: false }`. Идемпотентный 200
СПРОЕКТИРОВАН, его ломает только `42P10`. 409 заставил бы агента отличать «дубль»
от «ошибки» на своей стороне.

**Смоук против живого Postgres — часть фикса, а не проверка.** Юнит-стенд
(`stubDb`) возвращает заготовленный ответ и SQL не исполняет: именно поэтому
`ensureForDay` был «покрыт тестами» и при этом не работал НИ РАЗУ. Единственная
застава, которая видит `42P10`, — шаг `tools/smoke-core.mjs`: создание → повтор
тем же телом (200, пусто) → следующий день (новый `id`).

**Агент.** Слать реже не нужно — повтор с тем же ключом и ЕСТЬ механизм дедупа. Но
`errors` перестают быть строкой в `console.log`: при непустом списке прогон пишет
событие `maintenance.monitor_failed`. Сегодняшнее доказательство аварии пришлось
строить на схеме и нулевых счётчиках именно потому, что логи съело пересоздание
контейнера деплоем.

**Чем платим, если ошиблись.** В первый же прогон после выкатки (06:00 Ташкент)
появится до **19** задач обслуживания — это ожидаемо, это и есть починка, и
владельца предупреждаем заранее. Потолка на число задач за прогон срез НЕ вводит:
он относится к П7 (страховка автономии), и вводить его здесь значило бы прятать
первый честный результат за незнакомым порогом.

### R-G-3 Сторож свежести — в ОБОИХ режимах, поле витрины — own-only

**Решение.** Ранний `return` в `checkSnapshot` снимается: порог (36 ч), правило
(сырые часы), событие `ourvend.snapshot_stale`, дедуп по ташкентским суткам и
разбивка `which` — без изменений. Поле `OurvendHealth.snapshotStale`
(`ourvend-health.service.ts:222`) остаётся **own-only**, и различие записывается
докстрингом по ОБЕ стороны: у сторожа — «я про АГЕНТА: приносит ли
`ourvend:accounting` суточный снимок»; у поля — «я про УЧЁТ: остановился ли он от
этого; в режиме `stock` не остановился, продажи едут зеркалом».

**Почему.** В режиме `stock` снапшот теневой ДЛЯ УЧЁТА, но он единственный вход в
паритет (R-P8b-1), а паритет — гейт катовера. Вставший агент даёт «зелёную» серию
из нулей: ровно тот случай, когда ноль читается как «всё хорошо». Ложных тревог по
прод-данным не будет — агент опаздывает на минуты, а 36 ч это два пропущенных
съёма подряд.

**Чем платим, если ошиблись.** Владелец получит тревогу о таблице, которая до
катовера ни на что не влияет напрямую. Обратная цена — молчание про агента,
чьи снимки и есть предмет гейта; она дороже.

### R-G-4 `parityLastRed` и `parityStreakSince` — в здоровье, а не вторым запросом

**Решение.** `OurvendHealth` прирастает двумя полями рядом с
`parityStreak`/`cutoverThreshold`:

```ts
/** Дата последнего НЕзелёного дня по ВСЕМУ журналу (может лежать вне окна показа). null — красных не было. */
parityLastRed: string | null;
/** Первый день текущей серии. null — серии нет. */
parityStreakSince: string | null;
```

Имена с префиксом `parity*`, а не голые `lastRed`/`since`: в плоском объекте
здоровья `since` без контекста читается как «здоровье с такого-то момента».
Считать нечего — `серияПаритета` уже в `Promise.all`, добавление полей стоит НОЛЬ
запросов. `GET /ourvend/parity/streak` **остаётся**: он несёт `days[]` (пофакторный
разбор 14 дней), которого в здоровье нет и быть не должно. Убирается только ВТОРОЙ
ВЫЗОВ из двух витрин; вместе с ним уходят `.catch(() => null)`, то есть отказ
подсчёта серии больше не может отнять строку у здоровья.

**Почему.** Сегодня дата последнего сбоя стоит второго HTTP-раунда и исчезает
молча при его отказе. Поле уже вычислено — единственная причина, по которой
витрина ходит за ним отдельно, историческая.

**Чем платим, если ошиблись.** HTTP-контракт РАСШИРЯЕТСЯ, старые клиенты не
ломаются, порядок выкатки Core→витрины безопасен в любую сторону. Цена — 12 файлов
механических правок фикстур; их ловит ключ-гвард набора полей, а не глаз.

### R-G-5 Одна волна, четыре непересекающиеся задачи

**Решение.** Задачи 1–4 делаются ОДНОЙ параллельной волной, и ни один файл не
принадлежит двум задачам. Спорные границы разведены явно:

### R-G-6 Охват — ровно четыре задачи описи

**Решение.** В срез входят четыре пункта описи и ничего больше. Явно ВНЕ:
потолок числа задач за прогон монитора (это П7), правило/уведомление по событию
`maintenance.monitor_failed` (канал уведомления — решение владельца), унификация
кофейного резолвера `norm-fact.service.ts:402` и резолвера продаж
`sales.service.ts:518-666` (другие домены, другие таблицы, свои алиасные

**Почему.** Кофейный резолвер — четвёртое место, где живёт то же правило, и это

**Чем платим, если ошиблись.** Не взяв кофейный резолвер, оставляем долг записанным
и видимым. Взяв — получаем срез, который нельзя выкатить одним PR без отдельной
приёмки по кофе.

## 4. Общие ограничения (действуют на все четыре задачи)

* TypeScript strict, без `any`.
* Русский в UI, тестах и документации; идентификаторы — английские, экспортируемые
  имена общего слоя — латиницей.
* `now` — ПАРАМЕТР, а не `Date.now()` внутри (`check(now)`, `checkSnapshot(now)`,
  `streak(now)`, `health(runs, now)`), кеши, ключуемые временем, `now`
  ПРОБРАСЫВАЮТ.
* ПОКАЗ и РЕШЕНИЕ — разные числа: с порогом сравниваются сырые часы, владельцу
  уходит округление до 0.1 ч.
* Настройки — только через `apps/core/src/system/config-spec.ts`; ни одного нового
  `process.env` в Core. В этом срезе новых настроек НЕТ.
* `@Throttle` — только именованные лимитеры `burst`/`sustained`; новых роутов срез
  не заводит, троттлы существующих не трогает.
* Мутации — под `ServiceTokenGuard` (глобальный `APP_GUARD`), чтения внутри сети
  открыты; смоук шлёт `x-service-token`.
* Идемпотентность держится БАЗОЙ (уникальные индексы), а не `select` перед
  `insert`.
* Ноль ≠ «всё хорошо»: пустая выборка объясняется словами.
* `@mydon/shared` не знает ни о `@mydon/db`, ни о Nest — зависимость односторонняя.
* Комментарий объясняет ПОЧЕМУ и называет отвергнутую альтернативу; найденное
  проверкой на проде помечается прямо в коде.
* Документация правится ВНУТРИ задачи, которой она нужна.
* **Записей в прод из задач НЕТ.** ≈19 задач ТО появятся сами, первым прогоном
  агента после деплоя; примерку/запись бэкфилла делает владелец руками.

### Задача 1 — Единый резолвер каталога (M, R-G-1)

**`packages/shared/src/stock-history.ts`** — новая дверь рядом с `productIndex`:

```ts
/**
 * Ответ каталога с ИСТОЧНИКОМ решения и явным СПОРОМ.
 *
 * `raw` едет в `conflict`/`miss` намеренно: обе ветки печатаются владельцу
 * («это и имя карточки, и алиас другой», «карточки нет»), и без исходного
 * имени сообщение не собрать, а второй раз его никто не передаёт.
 */
export type CatalogResolution =
  | { kind: "hit"; canon: string; id: string; source: CanonSource }
  | { kind: "conflict"; raw: string; byName: string; byAlias: string }
  | { kind: "miss"; raw: string };

/**
 * ЕДИНСТВЕННАЯ дверь к правилу «сырое имя → карточка прайса» (R-G-1).
 *
 * Приоритет: ТОЧНОЕ имя карточки, потом алиас. Сравнение по
 * `normalizeProductName` (`ё`→`е`, схлопывание пробелов, запятая между цифрами
 * → точка). Алиас на СВОЮ же карточку спором не считается.
 *
 * Пустое/пробельное имя — `miss`, а не `hit` с пустым каноном: `resolveProductIds`
 * пропускает такие строки, и «привязать пустоту» здесь никогда не значило «нашли».
 */
export function resolveCatalogName(index: Pick<ProductIndex, "explain">, raw: string): CatalogResolution;
```

`productIndex.canon` и `.id` переписываются через неё (то же поведение: `hit → canon`,
`conflict → byName`, `miss → null`) — так импорт истории донора переиспользует
правило, не меняясь ни на строку.

**`packages/db/src/backfill-product-ids.ts`** — `resolveProductIds` зовёт
`resolveCatalogName(индекс, raw)` вместо `индекс.explain(raw)`; блок
«⚠️ ИЗВЕСТНОЕ РАСХОЖДЕНИЕ С ЖИВЫМ РЕЗОЛВЕРОМ CORE» (`:46-61`) заменяется ссылкой на
единый резолвер: расхождения больше нет, а долг закрыт этим срезом.

**`apps/core/src/vending/vending.service.ts`:**
- `loadProductIndex()` отдаёт `catalog: ProductIndex` **вместо** `aliasByKey` (те же
  две выборки, без второго SELECT). Компилятор находит все места, где канон
  считался мимо карточек, — это и есть смысл замены, а не сохранения поля рядом;
- `resolveProduct(name: string, catalog: ProductIndex): string` — `hit → canon`,
  `conflict → byName` + `logger.warn` («имя разрешается двумя путями»; на проде
  таких 0, и появление первого обязано быть видно), `miss → raw`;
- `productIdResolver` — `hit → id`, иначе `null`;
- `resolveProductRef` — `conflict → BadRequestException`, `miss → { name: raw, productId: null }`,
  `hit → { name: canon, productId: id }` (SELECT по имени больше не нужен);
- `resolveSlots(slots, catalog)` — тот же перевод.

**`apps/core/src/vending/analytics.service.ts:480`** — `canonOf` берёт `index.catalog`.

**`docs/DATA_SOURCES.md`** — абзац про резолв имени: правило ОДНО, живёт в
`resolveCatalogName`, приоритет «имя карточки > алиас», спор не привязывается и
печатается владельцу.
