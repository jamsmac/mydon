# VendHub: чтения остатков товаров — с таблицы `vending_stock` на складской леджер

Дата: 05.09.2026 · ветка `feat/goods-stock-reads-to-ledger` · продолжение У6 из
`2026-09-04-vendhub-parts-inventory-design.md` (§5.7, §12) и хвоста раздела 8 в `docs/OWNER_NEXT_STEPS_parts.md`.

## 1. Слово владельца (05.09.2026) — что должно быть

- «vending_stock оставь локально … и очисти сервер» → разобрано по коду: очистить нельзя, потому что
  таблица — не тень, а источник **списка позиций** и **дат пересчёта** для четырёх читателей, и даже в
  режиме `ledger` список берётся из её строк. Владелец согласился идти правильным путём.
- Три решения владельца (по вопросам 05.09):
  1. **Список позиций склада — прайс товаров** (`vending_product`, активные), остаток к каждой — из леджера.
  2. **Дата «когда считали» — из истории пересчётов** (`vending_stock_count`), а не из строки таблицы.
  3. **Объём среза — только чтения и сверка.** Теневая запись в таблицу остаётся, переключатель остаётся,
     откат — одной настройкой без рестарта. Снятие тени и удаление таблицы — следующий срез.
- Прод **не переключается** этим срезом: флип `VENDING_STOCK_SOURCE=ledger` остаётся за владельцем после
  недели нулевой сверки — но сверка после среза перестаёт быть ложно-зелёной, и «неделя» становится честной.

## 2. Что есть сейчас (проверено по коду 05.09) и что не так

Прод на момент спеки: `vending_stock` 24 строки · 167 единиц · последний пересчёт 01.09 · `vending_product`
52 позиции, все 52 связаны с карточками реестра (`entity_id`, миграция 0086 + `POST /stock/vending-cards`) ·
сверка `GET /stock/vending-parity`: 24 строки, расхождений 0, без карточки 0 · настройка
`VENDING_STOCK_SOURCE` не задана → действует `table`.

- Новый товар прайса появляется в остатках только после первого пересчёта: до него его как бы нет.
- Правило «откуда список и дата» размазано по четырём файлам.

**Писатели остаются как есть в этом срезе** (тень): пересчёт `vending.service.ts:1655`, приёмка накладной

**Что уже есть и переиспользуется:** `centralWarehouseId()`, `cardIdOf()`, `ledgerQty()`,

## 3. Инварианты (R-GS)

- **R-GS-1 Одна дверь.** Список позиций, остаток и дата пересчёта для товаров считаются в ОДНОМ месте —
  `goodsStock()` в леджер-слое. Ни один читатель не делает `select … from vending_stock` в режиме `ledger`
  и не вычисляет дату сам. (Прецедент правила — R-G-1 для канона имён товаров: три копии разошлись.)
- **R-GS-2 Прайс — список.** В режиме `ledger` перечень позиций склада = активные позиции `vending_product`.
  Товар без строки в таблице и без движений в леджере виден с остатком 0. Неактивный товар не показывается,
  но если у него ненулевой остаток в леджере — попадает в сверку (§6) как расхождение «неактивен с остатком».
- **R-GS-3 «Неизвестно» ≠ ноль.** Позиция без карточки склада (`vending_product.entity_id is null`) или при
  невыбранном центральном складе получает `quantity: null`. Закуп из такой позиции НЕ вычитает остаток и
  говорит об этом предупреждением; ноль означает «посчитали и пусто», а не «не считали».
- **R-GS-4 Переключатель честный.** `VENDING_STOCK_SOURCE=table` — поведение всех пяти мест без изменений
  (строка в строку). `=ledger` — все пять мест идут через одну дверь. Третьего режима нет.
- **R-GS-5 Сверка видит отсутствие.** Сверка перебирает объединение «активные позиции прайса ∪ строки
  таблицы». Позиция с ненулевым остатком в леджере без строки в таблице — расхождение. Пустая таблица при
  непустом леджере не может дать `mismatched = 0`.
- **R-GS-6 Дата — из истории.** `countedAt` позиции = максимум `dt` в `vending_stock_count` по `product_id`
  (фолбэк по `product_name` для строк до бэкфилла П4), `source ≠ 'storno'` и не отменённые
  (`reverses_id is null` и на них никто не ссылается). Нет ни одной — `null`.
- **R-GS-7 Один запрос на выдачу.** Остатки по карточкам берутся групповым запросом
  (`ledgerQtyMany(warehouseId, cardIds)`), не по запросу на позицию: план закупа считается на каждую сводку.
- **R-GS-8 Ничего не пишется.** Срез не добавляет ни одной записи и не меняет ни одной существующей записи
  в базу. Миграций нет.

## 4. Модель данных

Новых таблиц и колонок нет. Используются: `vending_product` (список), `entity` через `vending_product.entity_id`
(карточка склада), `stock_movement` по центральному складу (остаток), `vending_stock_count` (даты),
`vending_stock` (только в режиме `table` и в сверке).

Тип выдачи одной двери:

```ts
export interface GoodsStockRow {
  productName: string;          // имя карточки прайса (канон)
  productId: string;            // vending_product.id
  cardId: string | null;        // entity.id карточки склада; null — «без карточки»
  quantity: number | null;      // остаток по леджеру; null — неизвестно (R-GS-3)
  countedAt: Date | null;       // последний пересчёт из истории (R-GS-6)
  isActive: boolean;
}
export interface GoodsStock {
  warehouseId: string | null;   // null — центральный склад не выбран → все quantity = null
  rows: GoodsStockRow[];        // только активные (R-GS-2)
  asOf: Date | null;            // max(countedAt) по строкам
}
```

## 5. Потоки — что меняется у каждого читателя

### 5.1 Одна дверь: `goodsStock(db)` (`vending-ledger.ts`) + `VendingLedgerService.goodsStock()`

1. `warehouseId = centralWarehouseId()`; 2. `products = select … from vending_product` (все, с `is_active`,
`entity_id`); 3. `qtyByCard = ledgerQtyMany(warehouseId, cardIds)` одним `group by`; 4. `countedByProduct` —
один запрос `max(dt) … group by product_id/product_name` с фильтром R-GS-6; 5. сборка строк, сортировка по
имени `ru`. Без склада — шаг 3 пропускается, все `quantity = null`, `warehouseId = null`.

### 5.2 `stockLevels()` (читатель 1)

`table` → как сейчас. `ledger` → `goodsStock().rows` в форму `StockLevelRow`: `quantity ?? 0` **нельзя** —
`StockLevelRow.quantity: number` расширяется до `number | null`, `countedAt: string | null`. Потребители
`GET /vending/stock`: панель и бот показывают «—» вместо числа для `null`.

### 5.3 `stockRows()` → план закупа (читатель 2)

`table` → как сейчас. `ledger` → строки из `goodsStock()`; `StockRow` получает `quantity: number | null`.
В расчёте (`:2026+`): позиции с `null` НЕ попадают в вычитание из потребности и не в `unmatchedStock`, а в
новый список `unknownStock` → предупреждение плана «без карточки склада: N позиций — остаток не вычтен»
(текст рядом с существующим «склад устарел»). Сторож давности (`:2145–2170`): `asOf` = `goodsStock().asOf`;
`watched` исключает строки с `quantity === null`; в остальном логика прежняя.

### 5.4 Мёртвый сток (читатель 3)

`table` → как сейчас (`quantity > 0` из таблицы). `ledger` → `goodsStock().rows.filter(q > 0)`. Позиции
с `null` в отчёт не попадают и считаются в поле `unknown` сводки (панель показывает «N без карточки»).

### 5.5 Остаток в ответе заливки (читатель 4)

Обе ветки — свежая и повтор по `clientKey` — в режиме `ledger` берут остаток из `goodsStock()` по
`ledgerQty()` по карточке (`cardIdOf(productId)`), не собирая все 52 строки ради одной; без карточки —
`stockLeft: null`. Повтор больше не читает таблицу в режиме `ledger`. `stockLeft: number | null` — как сейчас.

### 5.6 Что НЕ меняется

Пересчёт склада (запись), приёмка накладной (запись), сторно, синк снабжения, история пересчётов
`GET /vending/stock-counts`, недельная сводка, ретенция — читают/пишут как раньше. Панель `/stock/goods`
и бот «🍫 Товары» в приёмке/инвентаризации — без изменений логики, только новые поля сверки (§6).

## 6. Сверка (читатель 5) — перестаёт быть ложно-зелёной

`vendingParity()` строит карту по **объединению**: активные позиции прайса (через `goodsStock()`, независимо
от переключателя) ∪ строки `vending_stock` (по `product_id`, фолбэк по нормализованному имени).

Строка сверки `VendingParityRow` расширяется:

```ts
{
  productName, productId, cardId,
  table: number | null,    // null — строки в таблице нет
  ledger: number | null,   // null — карточки/склада нет
  diff: number | null,     // table − ledger, когда оба известны
  status: "ok" | "mismatch" | "no_row" | "no_card" | "inactive_with_stock" | "no_warehouse";
}
```

Правила статуса, по порядку: нет склада → `no_warehouse` (все строки); нет карточки → `no_card`; нет строки
в таблице → `no_row` (независимо от остатка: это факт о таблице); неактивная позиция с `ledger ≠ 0` →
`inactive_with_stock`; иначе `diff = 0` → `ok`, `≠ 0` → `mismatch`.

Что считается расхождением: `mismatch`, `inactive_with_stock` и `no_row` **с `ledger ≠ 0`**. Позиция без
строки и с нулём в леджере — не расхождение (новый товар, который ещё не считали), но она видна как
`no_row`, чтобы отсутствие строк нельзя было принять за «всё сходится».

Сводка: `mismatched` — по правилу выше; `unlinked` — как раньше (`no_card`); новые счётчики `missingRows`
(все `no_row`) и `products` (позиций прайса в сверке).
Совместимость: `rows`, `mismatched`, `unlinked`, `warehouseId` остаются; `tools/import-warehouse-json.mjs`
и панель читают их как сейчас.

Панель `/stock/goods`: в строке — статус словами (`нет строки в таблице`, `без карточки`, `неактивен, но
есть остаток`), в шапке — `missingRows`. Текст `help` настройки `VENDING_STOCK_SOURCE`: «переключать, когда
сверка держится нулевой неделю **и позиций без строки нет**».

## 7. Экраны и UX

- `/stock/goods`: новые статусы в строках и счётчик в шапке; пустая таблица больше не выглядит как
  «Строк склада нет · Расхождений: 0» — будет «Позиций 52 · без строки 52 · расхождений 24» (24 — те, у
  кого в леджере ненулевой остаток).
- План закупа (панель, бот, чек-лист техника): новое предупреждение «без карточки склада: N — остаток не
  вычтен» в режиме `ledger`; в режиме `table` текстов не прибавляется.
- `GET /vending/stock` в `ledger`: все активные позиции, включая нулевые; `null` показывается как «—».

## 9. Тесты и приёмка

**Юнит (заглушка, `packages/*`/`apps/core` node:test):**
- `goodsStock()`: список = активные позиции прайса; позиция без карточки → `quantity null`; без склада →
  все `null` и `warehouseId null`; `countedAt` — max `dt` без сторно и отменённых, фолбэк по имени;
  `asOf` — max по строкам, `null` если никого не считали.
- `vendingParity()`: каждый статус §6 по одному кейсу; пустая таблица + леджер ≠ 0 → `mismatched > 0`,
  `missingRows = N`; таблица = леджер → 0.
- План закупа: строка `null` не вычитается и даёт предупреждение; строка `0` вычитается как ноль;
  сторож давности не считает `null` залежавшимся; `asOf` = `null` → «склад ни разу не считали» как раньше.
- `stockLevels()`/мёртвый сток/заливка: режим `table` — существующие тесты без правок (гарантия R-GS-4).

**Настоящий SQL (`tools/pglite-checks/check-parts-u6.mjs`, идёт в CI):**
1. Как сейчас: карточки, двойная запись, сверка 0/0 (без изменений — регресс).
2. **Пустая таблица при 2 позициях с остатком в леджере и 1 без движений** → `missingRows = 3`,
   `mismatched = 2`, статусы `no_row` у всех трёх.
3. Режим `ledger`: `stockLevels()` возвращает ВСЕ активные позиции, в т.ч. с нулём и без единого
   пересчёта; `stockRows()` вычитает остаток леджера в плане; мёртвый сток видит леджер; повтор заливки по
   `clientKey` отдаёт остаток леджера, а не таблицы.
4. Режим `table`: те же вызовы дают ровно прежние числа.
5. Позиция без карточки в режиме `ledger` → `quantity null`, план не вычитает и предупреждает.

**Дым (`tools/smoke-core.mjs`):** в режиме `ledger` `GET /vending/stock` и `GET /stock/vending-parity` отвечают
и содержат `status`/`missingRows`.

**Приёмка на проде (после мержа, без флипа):** `GET /stock/vending-parity` при `table` показывает
`missingRows = 28` (52 позиции прайса − 24 строки) и `mismatched = 0`, потому что у этих 28 остаток в леджере
ноль; панель говорит об этом словами. Это ожидаемо и не блокирует.

## 10. Риски

- **Закуп в режиме `ledger` меняет числа.** Только после флипа; до него — ни одной цифры не меняется
  (R-GS-4). Флип — владельцем, откат — той же настройкой.
- **Имена.** Сверка по объединению сопоставляет строки таблицы с прайсом по `product_id`, фолбэк —
  нормализованное имя через `resolveCatalogName` (R-G-1); сырая строка без карточки остаётся `no_card`, как
  сейчас.
- **История без `product_id`.** Строки `vending_stock_count` до бэкфилла П4 — фолбэк по имени; неоднозначных
  на проде 0 (замер 26.08 для алиасов).
- **Производительность.** Две группировки + один select вместо N запросов; план закупа кешируется 5 минут.

## 11. Вне среза

Снятие теневой записи (четыре писателя), удаление таблицы миграцией, флип прода, счётчик «дней нулевой
сверки» для товаров (аналог `parityStreak` OurVend) — следующие срезы, каждый после того как этот поживёт.
