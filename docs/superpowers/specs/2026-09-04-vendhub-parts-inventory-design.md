## 1. Слово владельца (04.09.2026) — что должно быть

1. Миксер не всегда моют на месте — **меняют на запасной**. Запасные есть у миксеров, гриндеров, варок
   (варочных узлов) и бункеров. Задача «помыть миксер» сегодня называет только автомат — а надо знать,
   **какой именно миксер** снят и куда ушёл.
2. У каждого узла — **свой инвентарный номер**, статус (в автомате · на мойке · в ремонте · на складе) и
   история возвратов.
3. Состав известен заранее: в каждом кофейном аппарате **4 миксера, 1 гриндер, 1 варка** и бункеры.
   Система сама заводит карточки узлов на весь парк (сейчас ~25 аппаратов; число берётся из реестра, не
   константой) — **без номера**. Кто откроет карточку — проставит номер или пропустит; следующему снова
   выйдет напоминание. Так номера проставляются постепенно.
4. **Инвентаризация**: владелец вводит по одному каждый узел, который лежит на складе или на мойке —
   с фото и серийным номером. Без номера завести можно, номер доставляется потом.
5. В остатках склада есть ингредиенты, но **нет товаров, которые перепродаются** (снек/напитки).
6. **Возвращённые с аппаратов бункеры** должны взвешиваться, а остаток — приходоваться на склад.
7. Посмотреть, как это сделано в старых репозиториях, взять лучшее, доработать, составить план — и делать
   всё подряд по порядку.

Это же закрывает открытый вопрос 3 полевого ТЗ (`FIELD_OPS_SPEC.md` §9: «ведутся ли серийники узлов и куда
девается снятая деталь») — ответ: ведётся **свой инвентарный номер**, серийник и фото — где есть; снятая деталь
уходит на мойку/ремонт/склад и остаётся в учёте.

## 3. Инварианты (R-PU)

- **R-PU-1 Узел — постоянная карточка, период — где он сейчас.** Новая таблица `part_unit` = физический
  экземпляр (миксер №M-017). `machine_part` остаётся историей периодов и получает `part_unit_id`. Идентичность
  узла **не зависит** от серийника и от номера: оба могут быть пустыми.
- **R-PU-2 Инвентарный номер — наклейка на детали, а не догадка системы.** `inventory_no` nullable, уникален
  в парке (без учёта регистра/пробелов). Система **предлагает** следующий свободный номер серии (`M-018`,
  `G-004`, `B-004`, `H-27-3`), человек подтверждает или вводит свой — тот, что на наклейке. Молча система номер
  не присваивает никогда.
- **R-PU-3 Автозаведение по составу.** Шаблон состава по виду автомата (`machine_kind`): кофе = mixer×4
  (слоты 1–4), grinder×1, brewer×1, hopper×(позиции с ингредиентом в `coffee_bunker_config`, иначе 8),
  water_filter×1. Заведение идемпотентно по ключу (автомат, вид, слот): повторный прогон ничего не дублирует.
  Заведённые карточки — без номера, с пометкой «заведено автоматически по составу».
- **R-PU-4 Напоминание о номере не гаснет.** Любая поверхность, где виден узел без номера (карточка автомата,
  карточка узла, пикер в мастере бота, закрытие задачи ТО), предлагает «Проставить № / Пропустить». Пропуск
  не запоминается как «больше не спрашивать» — следующему покажут снова. Плюс очередь «Без номера: N»
  (панель и бот) — прохождение по одному, как квиз ревизии.
- **R-PU-5 Статус вычисляется.** «В автомате / на складе / на мойке / на сушке / в ремонте / местонахождение
  неизвестно» = открытый период `machine_part`; «списан» = `retired_at` на карточке. Хранимого поля статуса
  нет — тот же принцип, что у сроков ТО.
- **R-PU-6 Фото — вложение узла.** `attachment.owner_type = 'part_unit'` (шильдик — `stage='plate'`), строки
  инвентаризации — `'part_count_line'`. При инвентаризации фото обязательно по умолчанию (настройка
  `vendhub.partCountPhotoRequired`, включена); пропуск фото допустим с причиной и виден в очереди «без фото».
- **R-PU-7 Инвентаризация узлов — сессия, применяемая одной транзакцией.** Черновик копится строками,
  «Применить» сверяет с открытыми периодами: найденные — подтверждены, новые — заведены, не найденные —
  переведены в «местонахождение неизвестно». Ничего не удаляется; отмена применения — обратной сессией.
- **R-PU-8 Замена по графику — два движения одного факта.** Закрытие задачи «Мойка миксера — Автомат N»
  = снят узел A (→ мойка) + поставлен узел B (со склада) одной транзакцией, оба движения помнят задачу.
  Норматив остаётся на автомате (`maintenance_plan` не меняется); факт — на узлах (`maintenance_log.part_unit_id`).
  Мойка снятого узла на базе — отдельная запись по узлу (мойка → сушка → склад), сроки автомата не двигает.
- **R-PU-9 Возврат бункера — это приход.** Нетто = брутто − тара узла; движение `return` в складской леджер
  на ингредиент бункера, партией «возврат из бункера H-27-3» с `opened_on = сегодня` — FEFO берёт её первой.
  Тара живёт на карточке узла (перенос из матрицы 27×8 при бэкфилле; матрица остаётся источником до У5).
- **R-PU-10 Один леджер для сырья и товаров.** Карточка `product` вида «на перепродажу» допускается в приход,
  перемещение, инвентаризацию и списание того же `stock_movement`. `vending_stock` становится **проекцией**
  леджера по центральному складу; до катовера — двойная запись со сверкой, после — только леджер.
- **R-PU-11 Ничего не удаляется, всё идемпотентно.** Каждый переход — запись `maintenance_log` / `stock_movement`
  с `client_key` (как у `vending_refill`); повтор кнопки в боте не даёт второго движения.
- **R-PU-12 Права — строками матрицы.** `parts.view`, `parts.number` (проставить номер), `parts.move`
  (снять/поставить/мойка), `parts.count` (инвентаризация), `stock.goods` (товары в леджере) — в
  `packages/shared/src/roles.ts`; по умолчанию у обоих полевых сотрудников всё, у владельца всё.

### 4.1 `part_unit` — карточка узла (новая)

### 4.2 Правки существующих таблиц

- `machine_part` + `part_unit_id uuid references part_unit` — NULL только на время бэкфилла (У1: колонка →
  бэкфилл → `not null` второй миграцией того же PR). Уникальный индекс «одно место — один открытый узел»
  остаётся; добавляется «**один узел — один открытый период**»: `unique (part_unit_id) where removed_on is null`.
- `part_location` + значение `unknown` (не найден при инвентаризации). `ALTER TYPE … ADD VALUE` — дёшево.
- `maintenance_log` + `part_unit_id` (NULL — работа по автомату целиком).
- `coffee_container_return` + `part_unit_id`, `ingredient_id`, `net_weight`, `stock_movement_id` (NULL до У5).
- `coffee_refill` + `part_unit_id` (NULL, если набор не записан).
- `stock_movement_kind` + `return` (возврат остатка со снятого бункера: +). `stock_batch.source` + `'return'`.
- `attachment.owner_type`: `'part_unit'`, `'part_count_line'` — без миграции (text).

### 4.3 Инвентаризация узлов (новые)

`part_count_session`: `id`, `location` (`part_location`, где считаем), `warehouse_id` (склад-`entity`, NULL для
мойки/ремонта), `started_at`, `finished_at`, `applied_at`, `reverses_id` (обратная сессия), `person_id`, `note`.

`part_count_line`: `id`, `session_id`, `part_unit_id` (NULL — узел не опознан → будет заведён), `part_kind`,
`inventory_no_entered`, `serial_entered`, `set_number_entered`, `hopper_position_entered`, `photo_skipped_reason`,
`result` (`found` · `new` · заполняется при применении), `created_by`, `created_at`. Фото — `attachment`.

Не найденные узлы в строки не пишутся: при применении их даёт разность «открытые периоды в этом месте −
строки сессии»; результат сохраняется в `maintenance_log` (kind `inspection`, note «не найден при
инвентаризации <дата>») и период переводится в `unknown`.

### 4.4 Состав автомата — настройка, не таблица

`system_config` ключ `vendhub.partsTemplate` (белый список `apps/core/src/system/config-spec.ts`), значение по
умолчанию — из донора:

```json
{ "coffee": [ {"kind":"mixer","count":4}, {"kind":"grinder","count":1}, {"kind":"brewer","count":1},
              {"kind":"hopper","count":"bunker_config"}, {"kind":"water_filter","count":1} ],
  "snack": [], "drink": [], "combo": [] }
```

Правится в панели (Система · Настройки). Изменение шаблона не удаляет узлы — только доводит недостающие.

### 4.5 Бэкфилл `machine_part` → `part_unit` (У1)

Правило восстановления нити узла из существующих периодов (`maintenance.service.ts`): `part_install` /
`part_remove` закрывают один период и открывают другой **того же** узла (общий `log_id`: `removed.remove_log_id =
stored.install_log_id`), `part_replace` — **разных** узлов. Одинаковый непустой серийник — тот же узел.
Всё остальное — отдельные узлы. Результат проверяется интеграционным тестом на настоящем Postgres
(образец — `packages/db/src/migration-0064.integration.ts`) с намеренно запутанными цепочками.

## 5. Потоки

### 5.1 Первичное заведение (после деплоя У2)

`tools/provision-parts.mjs --dry-run` → печатает по автоматам «заведём: 4 миксера, гриндер, варка, 7 бункеров,
фильтр»; без флага — `POST /parts/provision` (идемпотентно). Итог: N узлов без номера → очередь «Без номера: N».
Бункеры заводятся из наборов: если у автомата известен набор (последняя заливка с `container_number`) —
`set_number`/`hopper_position` и тара из матрицы; иначе — без набора, тара пустая.

### 5.2 Проставить номера — по одному

Панель `/maintenance?tab=parts:numbering` и бот «🔢 Номера узлов»: одна карточка на экран — автомат, вид, слот,
серийник/фото если есть, **предложенный номер** серии (следующий свободный); действия: *Проставить*
(предложенный или свой), *Пропустить*, *Списан / нет такого*. Тот же шаблон, что у квиза ревизии.
Напоминание в других местах (R-PU-4): бейдж «без номера» и кнопка «Проставить» на карточке автомата и в
пикере узлов мастера бота.

### 5.3 Замена миксера по задаче ТО (У3)

Задача монитора «Мойка миксера — Автомат 12» дополняется строками «Стоят: M-017 (слот 1), M-020 (2), — (3, без
номера), M-031 (4)». Закрытие в боте: выбрать снятый узел (список стоящих) → куда (мойка по умолчанию) →
поставить: со склада (список запасных этого вида: «M-044 · склад») или «новый узел» (карточка заводится сразу,
без номера — с напоминанием) → фото по желанию → **одна транзакция**: `maintenance_log(kind=cleaning,
part_unit_id=снятый)` + закрытие/открытие периодов + якорь графика сдвигается как сегодня.
Мастер «🔧 Замена детали» работает так же для любого вида узла.

### 5.4 Мойка на базе (У3)

Бот «🧼 Помыл»: список узлов «на мойке» → отметить помытые → «на сушку» или «на склад» (настройка
`vendhub.partDryingStage`, по умолчанию сушка есть) → `maintenance_log(kind=cleaning, entity=склад, part_unit_id)`
+ новый период. Панель: таблица «Мойка/сушка» с кнопками.

### 5.5 Инвентаризация узлов (У4)

Бот «📋 Инвентаризация узлов» → место (склад/мойка/сушка/ремонт) → цикл: вид → номер (ввести / нет) → серийник
(ввести / нет) → **фото** (или причина пропуска) → следующий / закончить. Панель показывает сессию живьём:
«найдено 12 · новых 3 · ожидалось 15». «Применить» — по R-PU-7. Владелец сказал «буду вводить по одному
каждый миксер, который на складе, на мойке» — это ровно этот цикл; серийник и номер необязательны.

### 5.6 Возврат бункера → склад (У5)

Строка «1. 027. 787» из группы → `recordContainerReturn` находит узел (набор 27, позиция 1) → тара с карточки
(или из матрицы) → нетто 787 − тара → ингредиент из парной заливки набора → `stock_movement(kind=return, +нетто,
батч «возврат из бункера H-27-1», opened_on)`. Если тары нет — возврат записывается как сегодня, без прихода,
и попадает в список «без тары» (карточка узла просит тару). Параллельно (тумблер `vendhub.coffeeRefillConsumes`,
по умолчанию выкл. до проверки) заливка списывает нетто со склада — закрывает пробел «coffee_stock не
уменьшается».

### 5.7 Товары на перепродажу в леджере (У6)

`cardOfType(…, "ingredient")` → допускает `product` с видом «на перепродажу»; единица — `шт`. Бот «📥 Приход»,
«📋 Инвентаризация», «🗑 Списать» показывают вкладки «Сырьё / Товары». Экран склада — две секции. `vending_stock`:
проекция леджера по центральному складу (`entity` warehouse c признаком «центральный»); `receiveOrder` и
подтверждение `vending_refill` пишут движения леджера, а не апдейт строки. Катовер — по образцу `CUTOVER.md`:
неделя двойной записи, сверка нулевая → переключение. JSON `vending-ops/warehouse.json` — первая инвентаризация
товаров через новый мастер (167 единиц как стартовые остатки).

## 9. Тесты и приёмка

- Юнит: серии номеров и `suggestInventoryNo` (пропуски, чужой формат, регистр); шаблон состава → недостающие узлы
  (идемпотентность, бункеры по конфигу); разность инвентаризации (найдено/новые/не найдены); нетто возврата и
  партия `return`; `cardOfType` для товара; проекция `vending_stock` = сумма движений.
- Интеграция (настоящий Postgres, CI): бэкфилл цепочек `machine_part` → `part_unit` на запутанных данных;
  уникальность «один узел — один открытый период» под гонкой двух установок.
- Смоук `smoke-core.mjs`: сквозной сценарий из §7.
- Приёмка владельцем: (1) после `provision` очередь «Без номера» = 14 × кофейных автоматов (± по конфигу
  бункеров); (2) проставить 3 номера с телефона за минуту; (3) закрыть задачу «Мойка миксера» с реальной заменой
  — карточки двух узлов показывают правильные места; (4) инвентаризация мойки на 5 узлов с фото — разность
  сходится; (5) строка «1. 027. 787» даёт приход нетто на склад; (6) товары видны в остатках склада и считаются
  при инвентаризации.

## 10. Риски

- **Бэкфилл угадает нить неверно** для узлов без серийников и без пары install/remove — по правилу §4.5 такие
  становятся отдельными карточками; это честнее склейки. Инвентаризация У4 их выправит (не найденные → unknown,
  найденные — привязка).
- **Двойной учёт бункеров** (матрица 27×8 и карточки) в переходный период — тара читается с карточки, при
  пустой — из матрицы; правка тары в панели пишет в оба места до У5 включительно, затем матрица только читается.
- **Катовер `vending_stock`** — единственный необратимый шаг; по образцу `CUTOVER.md` с неделей двойной записи
  и нулевой сверкой; откат — оставить `vending_stock` источником и выключить проекцию тумблером.
- **Дисциплина фото** — обязательное фото замедляет ввод; поэтому пропуск с причиной, а не запрет, и очередь
  «без фото» для дозаполнения.

## 12. Как сделано (as-built, 04.09.2026, ветка `feat/agentic-os-arms`)

Шесть коммитов У1–У6 поверх волны ARMS; все гейты зелёные (typecheck, lint, тесты: shared 853, db 170,
core 1769, agents 473, bot 828, cc 386; паспорта агентов; миграции и сценарии на pglite — `tools/pglite-checks/`).
Отклонения от текста выше и уточнения:

- **Номера (§5.2).** Система присваивает номер при заведении (`label_pending=true`), сотрудник нажимает
  «Наклеил» либо вписывает номер с детали. Бункер с известным набором — `H-<набор>-<поз>`; без набора —
  счётчик `H-001…`, который переименовывается в `H-набор-поз`, пока наклейка не подтверждена. Уникальность
  без учёта регистра и пробелов (`M-17` ≠ `M-017`: ведущие нули — часть номера). Состав — настройка
  `PARTS_TEMPLATE_COFFEE` (миксер 4, гриндер 1, варка 1, бункер 8, фильтр 1); автозаведение идемпотентно,
  свободный бункер набора со склада/мойки ставится обратно, а не дублируется.
  Узлам, которые бэкфилл 0084 восстановил из журнала БЕЗ номера (на проде 04.09 — 100 миксеров, 25 гриндеров,
  25 варок), автозаведение присваивает номер и ставит `label_pending` — в очереди внимания они и раньше висели
  как «без номера», но наклеить было нечего, а список печати (фильтр «наклеить») их не показывал. Прогон пишет
  `parts.number_assigned` на каждый номер ВНУТРИ транзакции автомата и отражает это в отчёте (`numbered`,
  `numberedTotal`) и в панели. Номера ведутся ОДНИМ списком за прогон, семя — все занятые номера базы без фильтра
  по виду (уникальность номера глобальная: `M-003` на карточке фильтра сдвигает серию миксеров), и каждый номер
  перед выдачей проверяется на занятость в обоих режимах — занят, берём следующий, а не рвём прогон посреди парка.
  Набор·позиция, занятые ранее в этом же прогоне, второму автомату не отдаются (иначе предпросмотр показал бы один
  номер наклейки на два бункера: набор кочует между точками через мойку). Поиск бункера набора смотрит и СПИСАННЫЕ:
  уникальность `(set_number, hopper_position)` их не исключает, и без этого прогон падал на индексе.
- **Замена по узлам (§5.3).** Мастер бота выбирает снятый узел по номеру из карточек автомата, спрашивает
  «куда увёз» (мойка первой для миксера/бункера/варки/гриндера) и запасной со склада или «новый»; на автомате
  без карточек — прежний путь (серийник → причина). `POST /maintenance/part-swap` принимает
  `slot / partUnitId / removedTo`. Задача ТО от монитора получает строку «Стоят: M-017 (№1), M-018 (№2)».
- **Мойка (§5.4).** `POST /parts/:id/washed` — мойка → сушка (или склад при `PARTS_DRYING_STAGE=0`),
  `POST /parts/:id/move` — сушка → склад, склад ↔ ремонт, с `clientKey`; узел на автомате не двигается.
  Бот «🚿 Помыл узлы» (одиночное «помыл» осталось за мойкой бункера на точке), панель — кнопки на карточке
  узла. Запись журнала идёт на автомат, с которого узел снят последним. Навык `parts-audit` у vendhub-ops
  (пн 08:30) — очередь внимания и мойка дольше 3 дней.
- **Инвентаризация (§4.3, §5.5).** Не найденные узлы при применении **записываются строками**
  `result=missing` (плюс `prev_*` для отката) — панель показывает их и после применения; текст §4.3 про
  «не пишутся» относится к вводу сотрудника. Найденный узел, числившийся в другом месте или на автомате,
  переводится сюда (на автомате — с записью журнала «снят по инвентаризации»). Фото строки при применении
  становятся фото узла. Откат — обратной сессией: не найденные возвращаются, перемещённые — где числились
  (занятое место на автомате — пропуск с причиной), заведённые остаются. Одна открытая сессия на место —
  бот продолжает её после обрыва.
- **Возврат бункера (§5.6).** `CoffeeLedgerService` (отдельно от `CoffeeService`, у того нет склада).
  Тара с карточки узла; из матрицы 27×8 берётся при её отсутствии и переносится на карточку. Причины
  непроведения: нет тары, брутто меньше тары, остаток нулевой, ингредиент неизвестен, у ингредиента нет
  карточки склада (`coffee_ingredient.entity_id`), склад приёма не выбран; список
  `GET /coffee/container-return/unposted`. Удаление возврата убирает и приход. Списание заливкой —
  `COFFEE_REFILL_CONSUMES=1` по умолчанию, только пачки × вес пачки или «после − до»; заливки без данных —
  `GET /coffee/refill/unconsumed`, досписать — `POST /coffee/refill/:id/consume`.
- **Товары (§5.7).** Мост прайса в реестр — `vending_product.entity_id` (миграция 0086, бэкфилл по имени);
  карточки для прайса заводит `POST /stock/vending-cards` (панель `/stock/goods`, dry-run). Двойная запись —
  `VendingLedgerService` (`@Optional()` в сервисах вендинга): приёмка → intake, заливка → consumption,
  сторно → adjustment, пересчёт → корректировка **от остатка леджера**. Тумблер катовера
  `VENDING_STOCK_SOURCE=table|ledger` переключает чтение (`stockLevels`, остаток в ответе заливки); строка
  `vending_stock` продолжает писаться и после катовера как тень — убрать её отдельным срезом, когда леджер
  поживёт. Сверка — `GET /stock/vending-parity`. Стартовые остатки — `tools/import-warehouse-json.mjs`.
- **Права.** `parts.number` (оператор, техник, кладовщик, менеджер), `parts.move` (оператор, техник,
  менеджер), `parts.count` (техник, кладовщик, менеджер).
- **Проверка.** Юнит-тесты пакетов + сценарии на pglite (`tools/pglite-checks/README.md`) + дымовой прогон
  `tools/smoke-core.mjs` («узел с номером — наклейка, замена по узлу, мойка, инвентаризация, возврат бункера»).
