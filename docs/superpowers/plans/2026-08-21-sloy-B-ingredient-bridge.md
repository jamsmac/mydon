# Срез B: мост ингредиентов + карточка ингредиента 360 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** связать бункерный контур кофе (`coffee_ingredient`) с реестром карточек
(`entity type=ingredient`), чтобы заливка бункера, рецепт товара и цена сырья
опирались на одну карточку, и дать этой карточке полноценный вид 360.

**Architecture:** мост (`coffee_ingredient.entity_id`), а НЕ слияние таблиц.
Причина — `deploy/auto-deploy.sh` делает `git reset --hard` до миграций, откатных
миграций у drizzle нет, упавшая миграция вешает автодеплой молча и навсегда.
Мост даёт непрерывную цепочку по внешнему ключу, но каждый шаг безопасен сам по
себе: колонка nullable, старый путь продолжает работать, гвардия в единственных
двух точках записи не даёт появиться новым сиротам.

**Tech Stack:** Drizzle + Postgres (packages/db), NestJS (apps/core), Next.js App
Router server components (apps/cc), grammY (apps/bot), чистый TS + `node --test`
(packages/shared).

**Spec:** `docs/PLAN_UCHET_SYRYA.md` §4 (Р2, Р4), §5 Срез B. Отклонения от текста
спеки перечислены ниже в «Ruling'ах», каждое с причиной.

## Установленные факты (проверены на живом проде 21.08.2026, не догадки)

1. `coffee_ingredient` — 8 строк, все бункерные: Сухое молоко, Ягодный чай,
   Лимонный чай, Матча, Сахар, Шоколад, MacCoffee, Кофе.
2. `entity(type=ingredient)` — 9 карточек: те же 8 имён **посимвольно** плюс
   «Стакан+крышка» (тара, не бункерный ингредиент). Совпадение имён 8/8 точное,
   нормализация не нужна.
3. **У всех 8 строк `coffee_ingredient.purchase_price` = NULL.** Цены живут
   только в карточках (`attrs["цена покупки"]`, с НДС). Поэтому себестоимость
   расхода в `reconcile`/`costOf` сегодня не считается вовсе — мост её чинит.
4. **Рецепты уже ссылаются на карточки:** `entity(product).attrs["состав"]` —
   19 кофе-товаров, `ingredientId` = `entity.id` ингредиента (проверено: Ice Lemon
   Tea → `50f4ff66…` = карточка «Лимонный чай», `0186782e…` = «Стакан+крышка»).
   Реестровая сторона среза B уже сделана; расколот только бункерный контур.
5. `coffee_product`, `coffee_sale`, `coffee_stock` — **0 строк** на проде.
   Их `recipe`-поле с конфликтующим смыслом `ingredientId` мёртво.
6. Единственные точки записи `coffee_ingredient`: `setIngredientPrice()`
   (`apps/core/src/coffee/coffee.service.ts:842-846`) и `addBunkerIngredient()`
   (там же, 857-871). Плюс seed-скрипт вне рантайма.
7. `packages/shared/src/recipe.ts` уже содержит `UNITS`, `convertQty`,
   `parseRecipe`, `recipeCost`, `IngredientPrice` — писать заново нечего.
8. `MANAGED_ATTR_KEYS` (`apps/cc/src/app/card/actions.ts:154-166`) НЕ содержит
   `"закупки сахара"` и `"альтернативы"` — массивы на живых карточках «Сахар»
   (3 чека) и «Сухое молоко» (Топпинг ALMAFOOD). Первая правка формой их теряет.

## Ruling'и по отклонениям от текста спеки

- **R-B1. Мост вместо слияния.** Спека §5 Срез B предлагает перевесить FK трёх
  таблиц и переименовать `coffee_ingredient` в `_legacy`. Делаем мост: колонка
  `entity_id`, FK трёх таблиц не трогаем. Цена ошибки: два id живут рядом ещё
  один срез; ломаться нечему, потому что старый путь не меняется.
- **R-B2. Миграция НЕ падает при неполном бэкфилле.** Спека требует «стопор
  8 из 8, иначе миграция падает». Обоснование стопора — не оставить наполовину
  перевешенные FK; при мосте половинчатости не бывает (null = «карточки нет»,
  код падает обратно на старый путь). Падающая миграция вешает автодеплой
  навсегда. Поэтому: бэкфилл best-effort + видимость несмапленных в UI и в
  `GET /coffee/bunker-config`. Цена ошибки: сирота проживёт до первого взгляда
  на экран, вместо того чтобы обрушить деплой.
- **R-B3. Цена — из карточки, `purchase_price` остаётся запасным путём.**
  Единый источник — `attrs["цена покупки"]` + `attrs["единица"]`. Цена ошибки:
  если у карточки цены нет, показываем старое поле, а не ноль.
- **R-B4. `coffee_product`/`coffee_sale`/`coffee_stock` не трогаем** — пустые,
  их судьба в срезе E. Цена ошибки: третий несогласованный смысл `ingredientId`
  живёт ещё срез, но в мёртвом коде.
- **R-B5. «Поставщик» на карточке остаётся плоской строкой** (так уже лежат
  данные), но в редакторе — выбор из существующих контрагентов (`<datalist>`),
  а в карточке 360 — ссылка на контрагента, если имя совпало. Ссылочного поля в
  jsonb не изобретаем: прецедента в проекте нет, а плоская строка совместима с
  тем, что уже введено. Цена ошибки: переименуют контрагента — ссылка отвалится,
  видно сразу, чинится одним словом.
- **R-B6. Три «срока годности» разведены.** В этом срезе — только норматив на
  карточке: `attrs["срок годности, дней"]` (число). Дата по факту поставки
  (`purchase.expiryDate` в mydon-stock) и `stock_batch.expiry_date` (срез C) —
  не трогаем и не смешиваем.
- **R-B7. Ключи не переименовываем.** `"закупки сахара"` остаётся как есть
  (переименование = правка данных на проде без выгоды сегодня); защищаем его и
  `"альтернативы"` в managed-списках.

```sql
-- Мост coffee_ingredient → entity(type='ingredient').
-- Бэкфилл по ТОЧНОМУ имени: на 21.08.2026 все 8 бункерных ингредиентов
-- совпадают с карточками посимвольно (проверено на проде). Миграция
-- сознательно НЕ падает на несовпадении: колонка nullable, старый путь
-- работает, а сирота видна на экране. Падающая миграция остановила бы
-- автодеплой без отката.
ALTER TABLE "coffee_ingredient" ADD COLUMN IF NOT EXISTS "entity_id" uuid;

DO $$ BEGIN
  ALTER TABLE "coffee_ingredient"
    ADD CONSTRAINT "coffee_ingredient_entity_id_entity_id_fk"
    FOREIGN KEY ("entity_id") REFERENCES "entity"("id");
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

-- Одна карточка — не больше одной строки бункерного реестра.
CREATE UNIQUE INDEX IF NOT EXISTS "ux_coffee_ingredient_entity"
  ON "coffee_ingredient" ("entity_id") WHERE "entity_id" IS NOT NULL;

UPDATE "coffee_ingredient" ci
   SET "entity_id" = e."id"
  FROM "entity" e
 WHERE e."type" = 'ingredient'
   AND e."name" = ci."name"
   AND ci."entity_id" IS NULL
   AND e."deleted_at" IS NULL;   -- сверь имя колонки мягкого удаления по schema.ts!
```

- [ ] **Шаг 1: тест сначала.** Значения — с живых карточек, не выдуманные:

```ts
import assert from "node:assert/strict";
import { describe, it } from "node:test";
import { cardPrice, pricePerGram } from "./ingredient-price";

describe("Цена ингредиента из карточки", () => {
  it("кг переводится в граммы", () => {
    // Кофе: 260 000 сум/кг с НДС → 260 сум/г
    assert.equal(pricePerGram({ "цена покупки": 260000, "единица": "кг" }), 260);
  });

  it("цена уже за грамм остаётся собой", () => {
    // MacCoffee: пакетик 20 г за 1600 → 80 сум/г
    assert.equal(pricePerGram({ "цена покупки": 80, "единица": "г" }), 80);
    // Сахар: дробная цена за грамм не округляется
    assert.equal(pricePerGram({ "цена покупки": 13.495, "единица": "г" }), 13.495);
  });

  it("штучная карточка не имеет цены за грамм", () => {
    // Стакан+крышка: 3600 сум/шт — вес тут смысла не имеет
    assert.equal(pricePerGram({ "цена покупки": 3600, "единица": "шт" }), null);
    assert.deepEqual(cardPrice({ "цена покупки": 3600, "единица": "шт" }), { price: 3600, unit: "шт" });
  });

  it("нет цены или единицы — null, а не ноль", () => {
    assert.equal(pricePerGram({ "единица": "кг" }), null);
    assert.equal(pricePerGram({ "цена покупки": 100000 }), null, "единица обязательна: 100 000 за кг и за грамм — разные деньги");
    assert.equal(pricePerGram(null), null);
    assert.equal(pricePerGram({ "цена покупки": "не число", "единица": "кг" }), null);
  });

  it("цена из строки с пробелами читается (карточки заводились руками)", () => {
    assert.equal(pricePerGram({ "цена покупки": "260 000", "единица": "кг" }), 260);
  });
});
```
