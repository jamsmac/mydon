# Полный аудит MYDON по всем направлениям (v2, 2026-08-31)

> Дополняет, а не заменяет `docs/AUDIT_PROMPT.md` (v1, точечный аудит домена
> VendHub с зафиксированными цифрами на момент написания). Этот промт шире:
> все домены, весь стек, плюс отдельный блок про совместимость и хвосты
> параллельной работы Claude Code и Codex. Цифры здесь намеренно не
> зафиксированы — ревизор обязан получить их сам, живыми запросами.

## 0. Как использовать этот документ

Это не один промт, а **комплект промтов для команды ревизоров** — по одному
на блок (раздел 3). Так собранный полный анализ проекта не утонет в
контексте одной сессии и не идёт «по памяти» вместо фактов.

**Как раздать:**
- Каждый блок (A–I) — самостоятельный `Agent`/новая сессия Claude Code
  с ролью «независимый ревизор, только чтение» (правила из раздела 1).
- Блоки A–D (данные и функциональность по доменам) независимы друг от
  друга → можно запускать параллельно.
- Блок I (совместимость Codex/Claude Code) и блок G (качество кода) лучше
  разными сессиями: I смотрит на историю и артефакты, G — на текущий код.
- Координатор (сессия, которая раздаёт блоки) в конце сводит все отчёты
  в один документ по формату раздела 4 — сам не проверяет ничего заново,
  только компонует.

**Инструменты и навыки под блоки:**
- Блоки A/E (данные, БД, миграции) — навык `supabase-postgres-best-practices`
  при вопросах по схеме/индексам/RLS-аналогах; прямые `psql`-запросы.
- Блок F (безопасность) — навык `security-review`, если доступен в сессии
  ревизора; иначе — ручная проверка по чек-листу раздела 3.
- Блок G (качество кода) — `pnpm typecheck && pnpm lint && pnpm test` по
  всему монорепо; при найденном баге — навык `systematic-debugging`
  для локализации причины, а не сразу патч (аудит = только чтение).
- Блок I (Codex/Claude Code) — агент `chat-historian`, если нужно свериться
  с тем, что реально обсуждалось/решалось в прошлых сессиях, а не только
  с тем, что осталось в коде.
- Для навигации по большому монорепо — агент `Explore` (быстрый read-only
  поиск) вместо ручного `grep` по всему дереву.

## 1. Правила проверки (обязательны для каждого блока)

1. **Не верь заявлению на слово.** Каждый факт — через запрос к БД, вызов
   API, открытие страницы, прогон тестов или чтение кода. Ссылка на этот
   документ или на память сессии — не доказательство.
2. **Только чтение.** Ничего не чинить, не удалять, не коммитить. Если для
   проверки нужна тестовая запись — создать, проверить, удалить, явно
   написать об этом в отчёте.
3. **Не выгораживать.** Пустой отчёт «всё хорошо» без цифр и фактов хуже,
   чем найденная проблема. Нашёл — пиши прямо, с последствием на практике.
4. **Отчёт — по-русски, для владельца без техфона.** «Страница не
   открывается», а не «404 на эндпоинте». Термин — только если без него
   никак, и сразу с пояснением.
5. **Секреты не выводить.** Только пути к файлам и факт «задан / не задан».
6. **Разделяй «не проверено» и «проверено, всё в порядке».** Если нет
   доступа (пароль, VPN, прод) — так и пиши: «НЕ ПРОВЕРЕНО, причина X».

## 3. Блоки проверки

### Блок A — Данные и целостность (домен VendHub)

Live-запросами к прод-БД получи текущие числа. Запрашивай активную базу
только через помощник (`ssh root@46.62.144.36
'/opt/backups/db_access.sh query "<SELECT>"' </dev/null`) — он ходит в
управляемую Supabase, где реально работает `mydon-core`; передавай только
чистый `SELECT` (сам помощник read-only не обеспечивает — см. раздел 2).
**НЕ используй
`docker exec mydon-db psql …`: `mydon-db` — recovery-копия с устаревшими
данными, числа из неё ложные.** Собери: товаров, автоматов, справочников
(ИКПУ,
упаковка, штрихкоды, классификатор, НДС), инкассаций (всего/принято/сумма),
продаж, партий прихода, снапшотов остатков, людей/агентов, записей в
audit_log. **Не бери числа из старого `docs/AUDIT_PROMPT.md` — они устарели.**
Сверь эти числа с тем, что показывает панель (`/vendhub` → Дашборд):
выручка сегодня/вчера, пустые позиции, ждут приёма. Расхождение — важная
находка.

### Блок B — Живая функциональность (домен VendHub)

Открой панель через Tailscale, проверь по-настоящему (не по описанию кода):
`/mydon`, `/tasks`, `/team`, `/approvals`, `/registry`, `/audit`,
`/domain/vendhub`, `/domain/globerent`. Внутри VendHub — вкладки Дашборд ·
Каталог · Справочники · Отчёты · Инкассация · Команда · Задачи; внутри
Каталога — Товары, Аппараты, Приход, Остатки в автоматах. Журнал товаров
(поиск, фильтры, «незаполненные»), карточка записи (паспорт → правка →
своё поле → удаление с подтверждением), карта автоматов (координаты,
цвета по типу, клик → карточка), инкассация (ожидающие/книга/итоги),
продажи (журнал 7 дней, плитка «молчат N+ дней»), остатки (пустые/на
исходе горят). Синки живые: `docker logs mydon-core --since 30m | grep -iE
"синхрон|снабжение"` — должны быть свежие записи.

### Блок C — Домен GLOBERENT

### Блок G — Качество кода (весь монорепо)

- `pnpm -w typecheck && pnpm -w lint && pnpm -w test` — сколько тестов,
  сколько падает. Если что-то красное — не чини, зафиксируй с полным
  выводом ошибки.
- `grep -rn ": any" apps packages --include="*.ts" --include="*.tsx" | grep -v node_modules | grep -v ".test."` —
  каждое совпадение либо оправдано (внешняя библиотека без типов) либо
  нарушение правила «без `any`».
- **Тихие сбои**: найди `catch` без `logger`/без эмиссии события —
  особенно в `apps/agents` и синках `apps/core/src/ourvend`,
  `apps/core/src/sales`, `apps/core/src/supply` (там уже находили один
  такой баг в T2 «Гигиены» — проверь, не появились ли новые).
  Прежде чем предлагать, что «просто добавить лог», используй навык
  `systematic-debugging`, чтобы отличить реальный тихий сбой от
  осознанно проглоченной неопасной ошибки.
- **Дублирование логики**: между `apps/core` и донорами (VendHub-OS,
  mydon_1, mydon-agent-os) — не осталось ли скопированного кода, который
  надо было адаптировать, а не тащить как есть (правило CLAUDE.md
  «перенос, не переписывание», но перенос без адаптации — тоже риск).
- **Конвенция форм CC** (`onSubmit`+`FormData`+`startTransition`,
  решение 24.08.2026): `grep -rn "action={" apps/cc/src --include="*.tsx"` —
  не откатился ли где-то код на React 19 `<form action={fn}>` (эта
  конвенция была принята именно потому, что откат теряет пользовательский
  ввод при ошибке).
- **Дрифт схемы БД**: `packages/db/drizzle/meta/_journal.json` против
  реально применённых миграций на проде — нет ли расхождения.

### Блок I — Совместимость и хвосты Claude Code / Codex

Проект развивался параллельно двумя инструментами (Claude Code — большая
часть истории; Codex — есть отдельная активность). Цель блока — не «чей
код лучше», а: не потеряна ли работа, нет ли конфликтующих решений,
не мусорят ли артефакты одного инструмента в рабочем дереве другого.

- **Ветка Codex**: воркдерево `~/Мой диск/1.AI /MYDON` на ветке
  `codex/parity-issues-task-domains` — сравни с `origin/main`
  (`git log codex/parity-issues-task-domains..origin/main` и наоборот).
  Влита ли она? Если нет — почему, есть ли конфликт с уже выкаченным
  `6ab1a47` (тот тоже про «parity tasks and domain grouping» — возможно,
  это ДУБЛИРУЮЩАЯ работа, сделанная дважды разными инструментами
  независимо. Проверь семантически, не только по имени ветки).
- **Незакоммиченные корневые файлы в `~/Developer/mydon`**:
  `AGENTS.md` (не отслеживается git, отсутствует в `origin/main` — похоже
  на черновик, начатый одним из инструментов; реши, актуален он или
  мусор), `.superpowers/HANDOFF-2026-08-26.md` (хендофф от Claude Code
  между сессиями — исторический, можно архивировать после сверки, что
  всё из него выполнено), `mydon-audit-2026-08-27.patch` (на момент
  этого промта уже не накладывается ни вперёд, ни назад — мёртвый
  артефакт, безопасно удалить после подтверждения, что содержимое либо
  уже в main, либо нигде не нужно).
- **7 stale worktree** со смёрдженными (squash) ветками:
  `mydon-audit-p0`, `mydon-audit-p0-refresh`, `mydon-inkass`, `mydon-p6`,
  `mydon-p7`, `mydon-vendcash-closeout`, `mydon-vendcash-shutdown-docs` —
  подтверди `git branch --merged origin/main` не покажет их (squash
  ломает эту проверку) — вместо этого сравни содержимое веток с main
  построчно по ключевым файлам, чтобы убедиться, что работа реально
  внутри, прежде чем предлагать `git worktree remove` + `git branch -D`.
- **Стиль/конвенции**: конвенция форм CC явно зафиксирована в CLAUDE.md
  как «миграция Codex принята осознанно» — значит расхождение стилей
  раньше уже было и разрешалось сознательно. Поищи другие места, где
  видно два разных почерка (например разный подход к error handling,
  разные паттерны тестов) — не для того чтобы унифицировать самостоятельно
  (это только аудит), а чтобы вынести решение владельцу.
- **Журнал миграций БД** (`packages/db/drizzle/meta/_journal.json`) —
  главный риск параллельной работы: если два инструмента одновременно
  создавали миграции, могли получиться дублирующиеся номера или miss в
  последовательности. Проверь непрерывность номеров и что каждая
  миграция в journal имеет файл на диске и наоборот.
- **История решений**: если что-то выглядит странно (например, два
  разных подхода к одному вопросу в разных PR), используй `chat-historian`,
  чтобы найти, обсуждалось ли это осознанно (тогда это решение, а не
  баг) или один инструмент просто не знал, что другой уже сделал это
  иначе.

## 4. Формат сводного отчёта (собирает координатор из отчётов A–I)

1. **Главное в пяти строках** — можно ли доверять системе по каждому из
