# Внешний сторож MYDON (обязателен по ТЗ §6)

Сервер mydon-os наружу ничего не открывает (всё на 127.0.0.1/Tailscale),
поэтому сторож работает по схеме **dead-man switch**: сервер сам каждые
2 минуты пишет отметку «я жив» в приватный GitHub Gist, а GitHub Actions
(другой провайдер, чем Hetzner) каждые ~10 минут проверяет её свежесть.
Отметка протухла → тревога в **отдельный** Telegram-бот: общий бот при
падении сервера лежал бы вместе с ним.

Слежка **взаимная**. Сторож на каждом прогоне пишет в тот же gist отметку о
себе, а сервер каждые 15 минут проверяет уже её. Без этого схема была
односторонней: смерть сторожа не видел никто, а умирает он тихо — сломанный
workflow, отозванный токен, отключённое Actions расписание (cron в
репозитории выключается после 60 дней без коммитов). Тишина при этом читается
как «всё хорошо» ровно тогда, когда проверять стало некому. Так уже было:
сторож падал на `checkout` и не проверил ни одного heartbeat.

```
mydon-os      ──(каждые 2 мин,  PATCH gist)──▶ heartbeat.json
GitHub Actions ──(каждые ~10 мин, читает)────▶ протухло? ──▶ 🚨 Telegram
GitHub Actions ──(каждый прогон, PATCH gist)─▶ watchdog.json
mydon-os      ──(каждые 15 мин,  читает)─────▶ протухло? ──▶ 🚨 Telegram
```

Оба контура лежат одновременно — не заметит никто, но это уже требует третьей
площадки и в схему не заложено сознательно.

## Настройка (один раз, ~10 минут)

1. **Gist**: https://gist.github.com → приватный gist, файл `heartbeat.json`,
   содержимое `{}`. Запомни id из адреса (`gist.github.com/jamsmac/<id>`).

2. **Токены** (github.com → Settings → Developer settings → Fine-grained tokens):
   создай **два** токена с единственным правом **Gists: Read and write**.
   Обоим нужна запись: сервер пишет `heartbeat.json`, сторож — `watchdog.json`
   в тот же gist. PATCH с одним файлом не трогает второй, поэтому они не мешают
   друг другу. Токены всё равно два — отозвать один, не трогая другой.

3. **Отдельный Telegram-бот**: @BotFather → `/newbot` → токен.
   Напиши новому боту `/start` и узнай свой chat_id (например, ботом @userinfobot).

4. **Сервер**:

   ```bash
   ssh root@100.81.197.68
   cat > /etc/mydon-heartbeat.env << 'EOF'
   HEARTBEAT_GIST_ID=<id из шага 1>
   HEARTBEAT_GH_TOKEN=<токен сервера>
   WATCHDOG_BOT_TOKEN=<токен бота из шага 3>
   WATCHDOG_CHAT_IDS="<chat_id, через запятую>"
   EOF
   cd /opt/mydon-app && ./deploy/setup-heartbeat.sh
   ```

   Файл читается через `.` (source), поэтому значения с запятыми и пробелами
   бери в кавычки — иначе строка развалится на команды и скрипт откажется
   стартовать.

   Скрипт поставит **два** systemd-таймера: heartbeat (2 мин) и
   watchdog-liveness (15 мин) — и сразу прогонит оба.

5. **Секреты Actions** (репозиторий → Settings → Secrets and variables →
   Actions → New repository secret):
   - `WATCHDOG_GIST_ID` — id gist;
   - `WATCHDOG_GH_TOKEN` — токен сторожа (Read **and write**: он отмечается в gist);
   - `WATCHDOG_BOT_TOKEN` — токен бота из шага 3;
   - `WATCHDOG_CHAT_IDS` — chat_id (через запятую, если несколько);
   - `WATCHDOG_STALE_MINUTES` — необязательно, порог (по умолчанию 10).

6. **Проверка сторожа**: Actions → workflow «watchdog» → Run workflow. В логе —
   «ok: heartbeat N мин назад». Потом останови таймер на сервере
   (`systemctl stop mydon-heartbeat.timer`), запусти workflow ещё раз —
   придёт 🚨; включи таймер обратно — следующий запуск пришлёт ✅.

7. **Проверка сторожа за сторожем**: на сервере
   `systemctl start mydon-watchdog-liveness.service && journalctl -u mydon-watchdog-liveness -n 5 --no-pager`
   — должно быть «ok: сторож отработал N мин назад». Чтобы увидеть тревогу, не
   ломая сторожа, хватит понизить порог на один прогон:
   ```bash
   WATCHDOG_LIVENESS_STALE_MINUTES=0 ./deploy/watchdog-liveness.sh
   ```
   Придёт 🚨; следующий обычный запуск пришлёт ✅ и вернёт состояние.

## Как это ведёт себя

- Тревога — при переходе «жив → лежит», напоминание — каждый запуск, пока
  лежит, «✅ снова жив» — один раз при восстановлении (состояние между
  запусками — в кэше Actions).
- В тревоге — последняя отметка: время, свободный диск, статусы контейнеров —
  видно, что умирало последним.
- Расписание Actions плавает (реально 10–15 мин) — это сторож «сервер лежит»,
  а не секундный мониторинг. Посекундная доступность — не его задача.
- Сторож за сторожем терпеливее: порог 45 минут переживает два подряд
  пропущенных прогона Actions, и тревога о нём повторяется не чаще раза в
  6 часов. Молчащий сторож — не авария, а слепое пятно; напоминание каждые
  15 минут приучило бы пролистывать, а одного сообщения в 03:00 мало.
- Если сервер не смог достучаться до gist (своя сеть, сбой GitHub), тревога о
  стороже НЕ поднимается: снаружи он в этот момент, скорее всего, жив, а вот
  наш heartbeat перестанет уходить — и тревогу поднимет уже он.
- На свежей установке отметки сторожа ещё нет, и это не авария: отсчёт идёт от
  первого запуска проверки. Но если сторож не отработал ни разу дольше порога,
  тревога придёт — «ни разу» не должно означать вечную тишину.
- Пороги и повтор настраиваются в том же env-файле:
  `WATCHDOG_LIVENESS_STALE_MINUTES` (45), `WATCHDOG_LIVENESS_REMIND_HOURS` (6).
- `apps/watchdog` (HTTP-пуллер) остаётся в репо: пригодится, если появится
  публичный healthz-endpoint или второй VPS для сторожа.
